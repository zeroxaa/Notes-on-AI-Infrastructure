# 第 5 章 yunyun 平台开发：从需求到架构

## 引子：平台是基础设施的产品化

基础设施再强，如果用户每次用都要手写 YAML、手动找机器、自己看日志，它的价值就发挥不出来。平台的作用是把基础设施封装成产品，让用户能自助地提交训练任务、部署推理服务、查看资源使用情况。

yunyun 是本书涉及的一个 AI 训推一体平台教学项目。它不是最终答案，而是一个典型案例：一个小团队如何从零开始，做出一个能跑起来的 AI 平台。本章通过它讨论平台开发中的关键判断点。

平台开发和普通应用开发不同。它既要服务终端用户，又要管理底层基础设施。产品经理和开发工程师必须同时理解用户诉求和系统约束。

## 5.1 平台要解决什么问题

一个 AI 平台的核心用户有两类：AI 研究员和大模型开发者。他们的需求可以归纳为：

**训练能力**：能够自助提交分布式训练任务，选择 GPU 数量、镜像、启动命令，查看日志和指标。

**推理能力**：能够把训练好的模型部署成在线服务，支持扩缩容和灰度发布。

**开发环境**：提供 Notebook 和虚拟机，方便调试代码和预处理数据。

**资源管理**：查看自己团队用了多少 GPU、还剩多少配额。

**多租户隔离**：不同团队之间的数据、资源、权限互相隔离。

这些需求听起来普通，但实现时需要把 Kubernetes、Volcano、KServe、存储、网络、监控、计费等多个系统串起来。每个系统都有自己的概念和接口，平台要做的是把这些复杂性藏起来。

平台用户不关心 Pod 怎么调度、PVC 怎么挂载、NCCL 怎么配置。他们关心的是能不能快速开始训练、训练挂了怎么排查、模型怎么部署成服务。平台设计要围绕这些用户目标展开，而不是围绕底层技术展开。好的平台让复杂基础设施变得易用，但不会因为易用而牺牲底层控制力。

## 5.2 需求分析：先写 PRD，再写代码

yunyun 的开发从 PRD 开始。PRD 是产品需求文档，回答"做什么"和"为什么做"，但不回答"怎么做"。

PRD 的核心组成部分包括：

**用户画像**：AI 研究员关注训练效率和实验可复现；大模型开发者关注推理延迟和部署灵活性。

用户画像不是简单贴标签，而是描述用户的角色、目标、痛点和使用场景。AI 研究员的典型场景是：上午提交一个 8 卡训练任务，下午查看 loss 曲线，晚上根据结果调整参数再跑一轮。大模型开发者的典型场景是：训练完成后把模型一键部署为推理服务，然后压测延迟和吞吐。

**用户故事**：用"作为……我想要……以便……"的格式描述需求。

**验收标准**：用"给定……当……那么……"的格式定义完成标准。

**优先级**：用 MoSCoW 法则把需求分为 Must have、Should have、Could have、Won't have 四类，再细化为 P0/P1/P2。

一个常见的错误是把 PRD 写成技术文档，在里面讨论数据库、API、框架选型。这些应该留在设计阶段。PRD 的边界是"做什么"，技术设计的边界是"怎么做"。

yunyun 的 PRD 围绕三大维度展开：AI 训练平台、多租户体系、多模型支持。功能覆盖训练、推理、Notebook、虚拟机、模型仓库、监控、计费、审批、通知等模块。三大维度覆盖了平台的核心价值：让用户能训、能推、能隔离。

### PRD 各章节示例

一份完整的 PRD 通常包含 12 个章节。下面是 yunyun PRD 的简化示例：

**1. 产品概述**

yunyun 是面向企业内部的 AI 训推一体私有云平台。它让 AI 研究员和大模型开发者能够自助使用 GPU 资源完成训练、推理、实验，无需关心底层 Kubernetes 细节。

**2. 用户画像**

AI 研究员：角色是训练大模型、部署推理服务、使用 Notebook 实验。目标是快速获取 GPU 资源、提交训练任务、部署模型服务。痛点是 GPU 资源申请慢、训练任务管理混乱、模型部署门槛高。

大模型开发者：角色是开发/微调大模型、管理模型版本。目标是模型训练到部署的全流程管理。痛点是模型版本管理分散、训练到部署链路断裂。

**3. 用户故事**

训练模块用户故事：

作为一名 AI 研究员
我想要提交分布式训练任务并监控训练进度
以便我能利用 GPU 集群高效训练大模型

**4. 验收标准**

AC1：Given 用户有 GPU 配额，When 提交训练任务，Then 返回任务 ID，状态变为 Pending。

AC2：Given Volcano 调度成功，When 所有 Pod Running，Then 状态变为 Running，可查看实时日志。

AC3：Given 训练完成，When Pod 退出码为 0，Then 状态变为 Succeeded，可查看训练指标。

AC4：Given 训练失败，When Pod 退出码非 0，Then 状态变为 Failed，可查看错误日志和 Events。

AC5：Given 用户配额不足，When 提交任务，Then 系统拒绝并提示配额使用情况。

**5. 需求优先级**

P0 / Must have：训练任务、推理服务、多租户/RBAC、用户认证、模型仓库。

P1 / Should have：监控告警、计费、审批、通知、日志、集群管理、CI/CD。

P2 / Could have：训练任务对比、推理 A/B 测试、成本分析。

Won't have：多集群联邦调度、全链路追踪、AIOps 自动根因。

**6-12. 功能详细/非功能需求/交互流程/数据需求/依赖约束/里程碑/风险**

这些章节进一步展开每个模块的详细功能、性能安全可用性要求、页面流转、数据模型概要、外部依赖、版本计划和已知风险。

**7. 非功能需求**

性能：训练任务列表查询响应时间小于 500 毫秒。并发：平台支持 100 个用户同时在线。可用性：平台服务可用性目标 99.9%。安全：所有 API 必须鉴权，敏感操作必须审计。

**8. 交互流程**

用户登录 → 选择集群 → 提交训练任务 → 查看任务状态 → 查看日志 → 任务完成 → 下载模型。异常路径包括配额不足、镜像拉取失败、调度超时等。

**9. 数据需求**

训练任务表、用户表、租户表、配额表、模型仓库表、推理服务表等。数据需求只描述业务实体和关系，不做具体数据库设计。

**10. 依赖约束**

依赖 Kubernetes 集群、Volcano、KServe、MySQL、Redis、对象存储。约束包括 NVIDIA 与昇腾集群物理隔离。

**11. 里程碑**

M1 完成用户认证和多租户。M2 完成训练任务模块。M3 完成推理服务模块。M4 完成监控和计费。

**12. 风险与开放问题**

风险：团队对 Volcano 和 KServe 不够熟悉。开放问题：是否需要支持昇腾 910B 的完整训练链路。

### 用户故事与验收标准的关系

用户故事描述"用户要什么"，验收标准定义"这个故事做到什么程度算完成"。一个用户故事通常有 3-7 条验收标准，覆盖正常路径和异常路径。

太少说明场景没想清楚，太多说明故事太大应该拆分。yunyun 的"提交训练任务"用户故事有 5 条 AC，覆盖正常提交、调度成功、训练完成、训练失败、配额不足。

验收标准用业务语言写，不写技术细节。比如写"返回任务 ID"，不写"调用 POST /api/v1/training 返回 JSON 中 code=0"。业务语言让产品经理、开发、QA 对完成标准有共同理解。

### MoSCoW 与 P0/P1/P2 的组合

MoSCoW 是分类法，不是排序法。它把需求分到四个桶里，同一桶内不需要精确排名。P0/P1/P2 是粗略排序，告诉团队这类需求大概什么时候做。

两者组合使用：先用 MoSCoW 判断哪些必须做、哪些不做，再用 P0/P1/P2 决定先做什么、后做什么。yunyun 的 16 个模块就是这样管理的。

MoSCoW 中 Must have 占比建议控制在 60% 左右。如果 80% 的需求都是 Must，说明把"很重要"和"必须做"混为一谈了。没有它产品就不能发布的需求才是 Must，很重要的需求可能是 Should。

Won't have 的价值同样重要。明确排除某些需求可以释放团队精力，避免在暂时不需要的功能上讨论和设计。Won't have 不是永远不做，而是这个版本不做。敢于说"这次不做"是优先级管理的高级能力。yunyun 明确把多集群联邦调度列为 Won't have，避免团队过早陷入复杂架构。

## 5.3 架构风格：模块化单体

yunyun 选择模块化单体架构。整个项目在一个代码仓库里，构建出两个二进制：server 和 worker。

server 处理 HTTP 请求，worker 处理后台任务。两者共享 model、service、repository 层，模块间通过 Go 接口隔离。

没有选择微服务，原因是：

**团队规模小**：教学项目团队不到 5 人，微服务的运维、部署、调试成本太高。

**模块边界清晰**：通过 Go 接口调用，编译时就能检查类型错误，不会运行时才发现问题。

**server 与 worker 通信简洁**：两者之间用 gRPC 通信，不引入服务发现和配置中心。

**未来可拆分**：当业务增长到需要独立部署时，模块之间的接口已经划定，拆分成本较低。模块化单体是"可拆分的单体"，不是"不能拆的单体"。

模块化单体的关键纪律是模块间通过 Go 接口调用，不能跨模块直接访问数据库或内部结构。如果违反这个纪律，系统会退化成普通单体，未来拆分困难。团队需要代码审查和静态分析来保证模块边界。

三种架构风格对比：

| 维度 | 单体 | 微服务 | 模块化单体 |
|------|------|--------|-----------|
| 进程数 | 1 | N | 2（server + worker） |
| 模块通信 | 直接函数调用 | HTTP/gRPC | Go 接口 + gRPC |
| 耦合度 | 高 | 低 | 中 |
| 运维复杂度 | 低 | 高 | 中 |
| 适合团队 | 3 人以下 | 20 人以上 | 5-10 人 |

架构不是选最新的，是选最合适的。

### 模块化单体与微服务决策 ADR

这个决策被记录为 ADR-008。ADR 是 Architecture Decision Record，用来记录每个重要架构决策的上下文、理由和后果。

ADR-008 的标准格式：

```markdown
# ADR-008: 模块化单体 vs 微服务

## 状态
已接受

## 背景
yunyun 是教学项目，团队小于 5 人，需要快速迭代。
后端 28 个模块，需要清晰的模块边界。
不需要独立扩展单个模块。

## 决策
采用模块化单体架构：
- 一个 Git 仓库
- 两个二进制：server（API）+ worker（后台任务）
- 模块间通过 Go 接口调用
- server 与 worker 通过 gRPC 通信

## 理由
1. 团队小，微服务运维成本过高
2. Go 接口编译时检查，比 HTTP 调用更安全
3. server 与 worker 共享 model/service/repository
4. 模块边界清晰，未来易拆微服务

## 后果
- 正面：开发快、部署简单、调试容易、代码复用
- 负面：需纪律保持模块边界，不能随意跨模块调用
- 后续：如果模块需要独立扩展，可拆成微服务
```

ADR 的价值在于决策可追溯。新人问"为什么用模块化单体"，可以直接看 ADR-008。未来团队变大、需要拆分微服务，也可以基于 ADR 重新评估。

yunyun 共有 11 条 ADR，覆盖框架选型、调度引擎、推理引擎、权限体系等核心决策。例如 ADR-001 选 Gin，理由是生态成熟、文档完善、70k+ GitHub stars。ADR-002 选 Volcano，理由是支持 gang scheduling 和层级队列。ADR-009 选 RBAC，理由是 10 角色 69 权限码能覆盖平台权限需求。

ADR 和架构设计文档不同。设计文档描述系统长什么样，ADR 记录为什么长这样。两者互补，缺一不可。没有 ADR，设计文档里的决策理由会随时间丢失。

ADR 编号不连续，因为 007 在开发中被废弃但保留编号。这本身也是 ADR 的价值：记录了"试过但放弃"的决策。

## 5.4 模块划分

yunyun 按业务领域拆分模块，后端大约有 28 个 handler，覆盖：

**用户与权限**：用户管理、RBAC、租户隔离、登录认证。

**训练任务**：任务提交、状态机、Volcano 集成、日志、指标。

**推理服务**：模型部署、KServe 集成、版本管理、扩缩容。推理服务的状态机与训练任务类似，也是 DB 一行 + K8s 一个 InferenceService + 状态机。这种"DB 行 + K8s CRD + 状态机"的架构模式在 yunyun 多个模块中复用。

**资源管理**：集群管理、节点管理、配额管理、队列管理。集群管理维护多个 K8s 集群的 kubeconfig，节点管理展示 GPU 节点状态，配额管理控制租户资源使用。

**平台通用**：通知、审批、计费、监控、日志。

这种划分方式让新增功能时知道该放在哪里，也让不同开发者负责不同领域时减少冲突。

### 模块三层结构

每个模块内部按 handler、service、repository 三层组织。

handler 处理 HTTP 请求，做参数校验和响应封装。service 处理业务逻辑，如配额校验、构建 Volcano Job YAML、调用 K8s API。repository 处理数据访问，如 GORM 查询、状态更新。

同进程内模块间通过 Go 接口调用。training service 调用 quota service 检查 GPU 配额，编译时就能发现接口不匹配。这种调用是同步函数调用，没有网络开销，也没有序列化成本。

跨进程的 server 与 worker 通过 gRPC 通信，worker 负责轮询 K8s 状态并同步到数据库。gRPC 提供类型安全和二进制序列化，比 REST 更适合内部服务通信。server 处理 API 请求，worker 处理后台任务，两者可以独立重启。

模块边界要严格遵守。不能为了让某个功能快一点，就绕过接口直接调用另一个模块的 repository。破坏模块边界会让系统变成事实上的单体，失去模块化单体的优势。

## 5.5 训练任务模块的设计

训练任务是平台最核心的模块。一个训练任务在 yunyun 里是"三位一体"：

![图01-训练任务三位一体](images/ch05/图01-训练任务三位一体.png)
*图 5-1：训练任务：DB 一行 + K8s VCJob + 状态机*

**数据库一行**：存业务元数据，包括谁创建的、用什么镜像、要几张 GPU、当前状态、队列、优先级等。

**K8s 一个 VCJob**：运行时资源由 Kubernetes 和 Volcano 管理，包括 Pod、Volume、调度策略。

**一个状态机**：描述任务从 Pending 到 Running，再到 Completed 或 Failed 的生命周期。

### 训练任务状态机详细转换

状态机不是只有几个状态，而是状态加上转换条件。什么事件触发什么状态变化，必须定义清楚。

yunyun 训练任务有四个状态：

**Pending**：任务已提交，等待 Volcano 调度。在队列排队，尚未分配 GPU。

**Running**：Pod 已调度成功，训练正在进行。GPU 已分配，容器在跑。

**Completed**：训练成功结束（exit code = 0）。终态，不可回退。

**Failed**：训练失败（OOM / 错误 / 超时 / 调度失败）。终态，可通过 retry 回到 Pending。

状态转换矩阵：

| 从状态 | 事件 | 到状态 | 触发者 |
|--------|------|--------|--------|
| Pending | Pod 调度成功 | Running | Worker 轮询发现 Pod Running |
| Pending | 调度超时 | Failed | Worker 检测超时 |
| Running | 训练成功（exit=0） | Completed | Worker 轮询发现 Pod Succeeded |
| Running | 训练失败（OOM/错误） | Failed | Worker 轮询发现 Pod Failed |
| Running | 用户手动停止 | Failed | Handler 收到 stop 请求 |
| Failed | 用户重试 | Pending | Handler 收到 retry 请求 |

Completed 是终态，不可转换。Failed 可通过 retry 回到 Pending 重新调度。状态转换由 Worker 异步轮询驱动，不是同步的。

Worker 每 30 秒轮询一次。查数据库找到 Pending 和 Running 的任务，查 K8s 获取 Pod 状态，映射到 yunyun 状态，再更新数据库。API 返回的是 DB 状态，可能滞后于 K8s 实时状态。

状态机的价值在于防止非法转换。比如 Completed 状态收到用户重试请求，状态机会拒绝，而不是允许重新启动已完成的任务。这保证了数据一致性，避免一个任务被多次启动或重复计费。

训练 API 不只是 CRUD，还包括状态机操作。启动、停止、重试都是 POST 请求，因为它们不幂等。CRUD 用 REST 标准方法，状态机操作用 POST 触发生命周期变化。

训练日志不存数据库，而是从 K8s Pod Logs API 实时拉取。日志量大、实时性高，不适合关系型数据库。通过 Volcano label selector `volcano-job=<k8s_job_name>` 找到 Pod，再调 Pod Logs API 拉取最近 N 行。

### 训练任务端到端流程

用户在前端提交训练任务，请求到达 server。Handler 做参数校验，从 JWT 提取 tenant_id 和 workspace_id。Service 先检查 GPU 配额，再查询目标集群信息，然后构建 Volcano VCJob YAML。YAML 中包含镜像、命令、GPU 数量、队列、优先级、NCCL 环境变量等。

Service 通过 client-go DynamicClient 创建 VCJob。VCJob 提交到 K8s 后，Volcano Scheduler 开始 gang 调度。同时 Service 把任务元数据写入数据库，状态为 Pending。

Worker 每 30 秒轮询一次。发现 Pod 调度成功后，把任务状态更新为 Running。训练过程中，用户通过平台查看实时日志。训练完成后，Worker 根据 Pod 退出码更新状态为 Completed 或 Failed。

整个流程涉及平台 API、K8s API、Volcano 调度、Pod 状态、数据库更新多个环节。平台的作用就是把这些环节串起来，让用户只看到简单的提交和查看界面。

## 5.6 多租户设计

多租户是平台能否在多个团队之间共用的关键。

![图02-四级租户隔离](images/ch05/图02-四级租户隔离.png)
*图 5-2：yunyun 四级租户隔离*

yunyun 采用四级隔离：

**Tenant（子公司/大部门）**：最高层隔离，不同 Tenant 的数据完全分开。

**Workspace（部门）**：一个 Tenant 下可以有多个 Workspace。

**Group（小组）**：Workspace 下的资源组。

**User（用户）**：最终使用者，拥有具体角色和权限。

每一层都有独立的资源配额和权限控制。所有数据库表都嵌入 tenant_id、workspace_id、group_id 字段，保证查询时自动隔离。

### 多租户 RBAC 设计

yunyun 采用 RBAC 权限体系，不是 ACL。RBAC 的核心是权限授给角色，用户通过绑定角色获得权限。

yunyun 定义了 10 个角色：

- platform_admin：平台管理员，拥有所有权限
- tenant_admin：租户管理员，管理本租户
- workspace_admin：工作空间管理员，管理本空间
- group_admin：小组管理员，管理本组
- researcher：研究员，创建训练任务和模型
- engineer：工程师，部署推理服务
- viewer：观察者，只读
- billing_admin：计费管理员
- cert_admin：证书管理员
- auditor：审计员，只读加审计日志

权限码按 `module:resource:action` 格式定义，共 69 个。例如 `training:job:create` 表示创建训练任务，`inference:service:scale` 表示扩缩推理服务。字符串格式比数字编号可读性更好，也便于在代码中搜索和维护。

用户和角色是多对多关系。一个用户可以绑定多个角色，权限取并集。权限检查在中间件中完成，顺序是 Auth 认证 → Tenant 注入 → Permission 授权。

tenant_id 不是外键，而是数据隔离字段。它从 JWT 中的 user_id 推导出来，由中间件注入 Context，Repository 用 GORM Scope 自动加 `WHERE tenant_id=? AND workspace_id=?`。开发者不能手动传 tenant_id，否则前端可以伪造越权。

### JWT 认证与权限中间件

yunyun 使用 JWT 做无状态认证。用户登录后服务端签发 Access Token 和 Refresh Token。Access Token 有效期 30 分钟，包含 user_id、tenant_id、roles。Refresh Token 有效期 7 天，只包含 user_id，用于刷新 Access Token。

JWT 本身不加密 Payload，只签名防篡改。必须配合 HTTPS 传输，防止中间人截获 Token。额外安全措施包括 Access Token 短期有效、Refresh Token 不直接访问 API、Token 黑名单处理登出。

权限中间件在 Auth 之后执行。它从 Context 取 user_id，查用户绑定的角色，再查角色拥有的权限码，最后判断当前请求是否需要这些权限。没有权限返回 403 Forbidden。

认证和授权是两个不同概念。认证回答"你是谁"，授权回答"你能做什么"。中间件顺序不能颠倒，没认证就不能授权。

### 资源配额

每个租户有 GPU、CPU、内存的配额限制。创建训练任务时，Service 层先检查 `used_gpu + new_gpu <= quota.gpu_limit`。检查和创建要在同一事务内，防止并发超配。

配额检查放在 Service 层而不是数据库层，因为配额是业务规则，不是数据完整性约束。已用 GPU 是动态变化的，需要实时计算。用数据库事务保证检查配额和创建任务的原子性，避免两个并发请求同时通过配额检查。

### 多租户隔离模型

yunyun 使用共享数据库共享 Schema 的隔离模型。所有租户数据在同一张表，用 tenant_id 字段区分。这种模型成本低、运维简单、跨租户统计方便，但隔离弱点是 SQL 忘加 WHERE 就泄露数据。

yunyun 通过中间件自动注入 tenant_id 弥补这个弱点。Auth 中间件解析 JWT 拿到 user_id，Tenant 中间件查用户表拿到 tenant_id 注入 Context，Repository 用 GORM Scope 自动加 WHERE 条件。开发者不需要手动写 tenant_id，避免遗漏。

独立数据库和独立 Schema 隔离更强，但成本更高。独立数据库适合金融、医疗等强合规场景。yunyun 面向企业内部 AI 平台，租户数有限，共享数据库共享 Schema 是合理选择。

## 5.7 从半成品到生产

yunyun 的定位是一个"半成品教学项目"。它的代码层面已经完成：后端 28 个模块、前端三平台、go vet 和 vue-tsc 零错误。但离生产系统还有距离：

**高可用**：数据库、缓存、消息队列需要多副本和故障转移。server 需要多实例部署，worker 需要 Leader Election 防止重复轮询。

**安全加固**：API 鉴权、审计日志、密钥管理、网络安全策略。Pod Security Standards 和 NetworkPolicy 需要启用。

**备份恢复**：任务配置、模型文件、数据库都需要备份策略。MySQL 主从、Redis 哨兵、etcd 备份要补上。

**事件驱动**：当前 Worker 可能是轮询状态，生产环境应使用事件驱动，提高效率。可以用 Kafka 或 K8s Watch 机制。

**可观测性**：接入 Prometheus、Grafana、Loki，建立完整的监控告警体系。包括业务指标、系统指标、日志聚合。

### 平台从半成品到生产清单

从半成品到生产，yunyun 至少需要补齐以下清单：

1. 数据库高可用：MySQL 主从 + 自动故障转移
2. 缓存高可用：Redis 哨兵或集群模式
3. 应用多副本：server 至少 2 实例，worker Leader Election
4. 密钥管理：JWT secret、数据库密码、K8s kubeconfig 接入 Vault 或 sealed secrets
5. 审计日志：记录所有敏感操作，包括登录、任务创建、权限变更
6. 网络安全：启用 NetworkPolicy，限制跨租户 Pod 通信
7. Pod 安全：启用 Pod Security Standards，限制特权容器
8. 数据备份：数据库定时备份，模型文件多副本
9. 事件驱动：Worker 从轮询改为 K8s Watch + Kafka
10. 监控告警：Prometheus + Grafana + Alertmanager + Loki
11. 计费精度：GPU 使用精确到分钟，生成月度账单
12. 灰度发布：平台自身升级需要金丝雀或滚动发布
13. 容量规划：根据用户增长预估数据库和缓存容量
14. 灾难恢复：制定 RTO 和 RPO 目标，定期演练
15. 安全审计：定期扫描依赖漏洞，及时升级
16. 文档完善：运维手册、用户手册、API 文档齐全

这些不是教学项目的重点，但任何想把平台投入使用的人都需要补上。清单中的每一项都有成本，团队需要根据实际情况分阶段补齐。

生产化过程没有统一终点。有些团队对可用性要求高，会优先做高可用和备份。有些团队对成本敏感，会优先做计费和资源优化。yunyun 的半成品定位就是让学生理解核心架构后，能根据自己企业需求继续完善。 checklist 只是起点，不是终点。

## 5.8 这一环在整个链路中的位置

平台层把底层基础设施包装成用户可用的服务。

向下，平台依赖 Kubernetes、Volcano、存储、网络、GPU 设备管理。如果这些基础设施不稳定，平台做得再好也无法提供服务。平台团队需要与基础设施团队紧密协作。

向上，平台面向 AI 研究员和开发者。它决定用户能以多低的成本使用资源，也决定运维团队能以多高的效率管理资源。

平台开发不是纯技术问题，也是产品设计问题。PRD、架构决策、模块边界、多租户模型，这些选择会长期影响系统的演进方向。好的平台让底层复杂性对用户不可见，同时给运维团队足够的控制力。平台设计要在用户体验和系统约束之间找到平衡。

## 小结

yunyun 的案例说明，做一个 AI 平台不只是技术栈选型。先写 PRD 明确需求，再选模块化单体平衡开发速度和可维护性，用 ADR 记录关键决策，按业务领域拆分模块，用状态机和多租户 RBAC 支撑核心业务，最后还要知道从半成品到生产需要补齐哪些清单。平台层的质量决定了底层基础设施能不能被高效使用。下一章将讨论 SRE 和变更规范，这是保证平台和基础设施稳定运行的关键保障。
