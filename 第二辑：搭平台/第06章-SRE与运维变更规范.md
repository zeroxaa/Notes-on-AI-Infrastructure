# 第 6 章 SRE 与运维变更规范

## 引子：系统不会因为有人值班而变可靠

很多人以为运维就是守着屏幕，出问题赶紧修。但靠人盯着，系统不会真正变可靠。人反应再快，也比不上自动化；人记性再好，也记不全每次变更的细节。

SRE（Site Reliability Engineering）的核心思路是用软件工程方法解决运维问题。它关心的不是某一次故障怎么处理，而是怎么让系统整体更稳定、怎么减少重复劳动、怎么让变更可控可逆。

在 AI Infra 场景里，SRE 尤其重要。GPU 集群规模大、训练任务时间长、故障影响面大，传统手工运维无法应对。一个训练任务跑几周，中间节点故障、网络抖动、OOM 都可能发生。靠人工 24 小时盯着不现实，必须靠自动化和自愈机制。

SRE 和 DevOps 有联系也有区别。DevOps 是文化理念，强调开发和运维协作。SRE 是具体实践方法，是用工程手段实现 DevOps 目标。可以把 SRE 理解为 DevOps 的一种实现路径。

SRE 不是让运维人员写代码那么简单。它要求团队用软件工程思维看待运维问题：把重复操作抽象成脚本，把脚本抽象成平台，把平台抽象成自愈系统。每一层抽象都减少人工干预，提高可靠性。

## 6.1 SRE 与传统运维的区别

传统运维的目标是让系统保持运行，方法以手工操作和脚本为主。SRE 的目标是在保证可靠性的同时提升工程效率，方法以代码和自动化为主。

| 维度 | 传统运维 | SRE |
|------|----------|-----|
| 工作方法 | 手工 + 脚本 | 软件工程 |
| 核心目标 | 保持运行 | 可靠性 + 效率 |
| 重复工作占比 | 高 | 低 |
| 变更执行 | 人工 | 自动化流水线 |
| 故障处理 | 人工排查 | 可观测性 + 自动响应 |
| 知识沉淀 | 口口相传 | Postmortem 文档 |

### 对比细节：GPU 掉卡场景

一个具体例子：GPU 掉卡。

传统运维：告警响起，人工登录节点，执行 nvidia-smi，确认后手动 cordon 节点、drain Pod、打标签隔离。整个过程依赖值班人员的经验和响应速度。

SRE：告警自动触发脚本，cordon 节点、drain Pod、打标签，同时通知值班人员，事后生成 Postmortem 分析根因。人工只负责确认和复杂判断，重复动作交给自动化。

GPU 掉卡在智算中心不算罕见。根据大规模 H200 集群运维经验，2048 卡 24 小时内约有 2-3 张 GPU 卡出现故障需处理。如果集群有 1000 张卡，平均每天 1-1.5 张，一年累计数百次。传统运维每次都要人工处理，SRE 通过自动化脚本把恢复时间从十几分钟降到几分钟。

SRE 不仅处理故障，还追求减少故障。通过 Postmortem 分析掉卡根因，可能发现某批 GPU 固件有缺陷，从而推动批量升级或隔离。这种从单个故障到系统改进的循环，是 SRE 的核心价值。

### Toil 与 50-50 原则

SRE 强调消除 Toil。Toil 是可自动化、重复、无持久价值的运维工作。Google SRE 建议 Toil 占比不超过 50%。如果团队 70% 时间都在做重复手工操作，说明系统设计有问题，需要工程化改进。

50-50 原则是指 SRE 时间分配：50% 做工程改进，50% 做运维响应。工程改进包括自动化、可观测性、平台工具。运维响应包括处理告警、值班、故障恢复。

在 AI Infra 场景，Toil 的典型来源包括：手动重启训练任务、手动隔离 GPU 节点、手动清理磁盘、手动扩容节点。这些都应该逐步自动化。

### 自动化四层级

自动化不是一步到位，通常经历四个层级：

**Level 1 手动操作**：人登录服务器执行命令。这是传统运维的主要方式。

**Level 2 脚本化**：写成脚本，手动触发。脚本减少了操作失误，但仍需人启动。

**Level 3 平台化**：集成到平台，通过按钮或 API 触发。yunyun 的运维平台 API 就是这一层。

**Level 4 自愈**：告警触发，自动执行。例如 DCGM Xid 告警自动隔离 GPU 节点，无需人工干预。

层级越高，响应越快，但建设成本也越高。团队应该优先自动化最高频的 Toil。

识别 Toil 的方法是看它是否满足三个特征：重复性、可自动化、无持久价值。手动重启服务、每周清理磁盘、手动扩容节点都是典型 Toil。排查新问题、设计监控系统、编写 Postmortem 不算 Toil，因为它们需要工程思考或有持久价值。

如果团队 Toil 比例长期超过 50%，说明系统设计有问题。此时应该停下来统计 Toil 来源，按频率和耗时排序，优先自动化最高频的部分。

AI Infra 团队常见的 Toil 来源还包括：手动处理 NCCL timeout 导致的训练卡住、手动调整 Volcano 队列权重、手动清理满磁盘节点、手动重启推理服务 Pod。这些都可以通过脚本、平台或自愈机制逐步消除。

## 6.2 SLI、SLO、SLA

SRE 用指标把可靠性量化。常见三层体系：

![图01-SLI-SLO-SLA层级](images/ch06/图01-SLI-SLO-SLA层级.png)
*图 6-1：SLI → SLO → SLA 层级*

**SLI（Service Level Indicator）**：服务等级指标，是实际测量值。例如过去 5 分钟推理服务请求成功率为 99.95%。

**SLO（Service Level Objective）**：服务等级目标，是团队设定的目标。例如推理服务可用性不低于 99.9%。

**SLA（Service Level Agreement）**：服务等级协议，是对外的合同承诺。通常会写得比 SLO 宽松，留出内部缓冲。

### SLO 数值计算示例

SLO 与可用性对应关系：

| SLO | 每月允许不可用 | 每年允许不可用 |
|-----|---------------|---------------|
| 99% | 438 分钟 | 87.6 小时 |
| 99.9% | 43.8 分钟 | 8.76 小时 |
| 99.99% | 4.38 分钟 | 52.6 分钟 |
| 99.999% | 26.3 秒 | 5.26 分钟 |

计算方式：每月按 30 天计算，总分钟数为 43200。99.9% 可用性允许 0.1% 不可用，即 43200 × 0.001 = 43.2 分钟。表中 43.8 分钟是更常用的近似值，按每月 30.44 天计算。

每多一个 9，投入大致增加一个数量级。不是 SLO 越高越好，而是根据业务需求和成本选择合适的 SLO。100% SLO 不现实，因为它意味着任何变更都不能做。

SLO 设置过高会束缚团队手脚。如果推理服务 SLO 设为 99.99%，每月只有 4.38 分钟容错。一次小规模发布就可能消耗大半预算，团队不敢迭代。SLO 设置过低则影响用户体验。需要根据业务重要性和成本承受能力找到平衡点。SLA 通常比 SLO 更宽松，给内部留出缓冲空间。

### AI Infra SLI 示例

推理服务 SLI：

- 请求成功率：成功请求数除以总请求数
- P99 延迟：99% 请求响应时间低于该值
- 可用性：服务可访问时间比例

训练平台 SLI：

- 任务完成率：完成任务数除以提交任务数
- 调度成功率：成功调度任务数除以提交任务数
- 平均调度等待时间：从提交到 Running 的时间

SLI 应该选择用户感知的指标，而不是技术指标。用户关心请求是否成功、是否够快，不关心 CPU 利用率。选择太多 SLI 会分散注意力，每个服务通常只需要 2-4 个核心 SLI。

### SLI 计算示例

假设推理服务一个月总请求数为 1000 万，失败请求数为 1 万。请求成功率 SLI 为：

(10000000 - 10000) / 10000000 = 99.9%

如果 SLO 目标是 99.9%，这个月刚好踩线。这说明系统已经接近可靠性边界，下个月应该减少激进变更。

再比如训练平台一个月提交 200 个任务，成功完成 190 个。任务完成率 SLI 为：

190 / 200 = 95%

如果 SLO 目标是 95%，这个月刚好达标。如果连续几个月都接近 95%，说明集群稳定性需要提升。

SLI 应该用 PromQL 等查询语言持续采集。例如推理服务成功率可以用：

```
sum(rate(http_requests_total{service="inference",code!~"5.."}[5m]))
/ sum(rate(http_requests_total{service="inference"}[5m]))
```

## 6.3 黄金信号与可观测性

Google SRE 提出的四个黄金信号：

**Latency（延迟）**：请求处理时间。推理服务关注 P99 延迟。训练任务关注 data_time 和每个 step 的耗时。

**Traffic（流量）**：请求量。推理服务关注 QPS。训练集群关注任务提交量、GPU 利用率。

**Errors（错误）**：错误率。网络通信关注丢包、重传、NCCL timeout。推理服务关注 5xx 错误率。

**Saturation（饱和度）**：资源使用程度。GPU 显存、网络带宽、磁盘 IO 是否接近上限。饱和度告警通常比错误告警更前置。

可观测性靠三大支柱：

**指标（Metrics）**：时间序列数据，用于告警和趋势分析。Prometheus + Grafana 是常见组合。

**日志（Logs）**：事件明细，用于故障定位。Loki 或 ELK 是常见组合。

**链路追踪（Traces）**：请求在系统中的完整路径。推理服务调用链较长时特别有用。例如用户请求经过网关、推理服务、模型加载、后处理多个环节，Tracing 可以定位哪个环节耗时最长。

可观测性不是三者都要做到极致。对于训练平台，指标和日志最重要，Tracing 相对次要。对于推理服务，三者都很重要。

### 黄金信号解读示例

假设推理服务 P99 延迟从 200ms 上升到 800ms。查看四个黄金信号：Latency 异常；Traffic 可能不变；Errors 可能轻微上升；Saturation 中 GPU 显存接近上限。根因可能是显存不足导致推理批处理大小下降，从而延迟升高。

再比如训练任务大量失败。Latency 体现为训练时间变长；Traffic 体现为任务提交量；Errors 体现为失败率；Saturation 体现为网络或 GPU 饱和。结合这些信号可以快速定位是网络问题、存储问题还是 GPU 硬件问题。

### 可观测性体系建设

可观测性不是简单地把 Prometheus 和 Grafana 装上，而是建立"采集-存储-查询-告警-可视化"的完整链路。

**指标采集**：Prometheus 通过 exporter 采集节点、Pod、GPU、网络设备指标。DCGM Exporter 采集 NVIDIA GPU 指标，Node Exporter 采集节点指标，自定义 exporter 采集业务指标。

**日志采集**：Fluentd 或 Promtail 把容器日志送到 Loki 或 ELK。训练任务日志量大，需要设置合理的保留策略和索引策略。

**告警规则**：告警要分层。页面告警用于需要立即响应的问题，如推理服务宕机。邮件告警用于需要关注但不必立即处理的问题，如磁盘使用率超过 80%。

**可视化**：Grafana  Dashboard 按角色组织。平台运维看集群资源大盘，算法工程师看训练任务指标，SRE 看 SLO 达成情况。

## 6.4 错误预算

SLO 的本质是"允许出错的额度"。99.9% 可用性意味着每月最多允许 43.8 分钟不可用。这个额度称为错误预算。

错误预算消耗快时，应该暂停非必要变更，优先提升稳定性。错误预算是 SRE 管理变更节奏的核心工具。

错误预算消耗决策：

| 预算消耗 | 决策 |
|----------|------|
| < 25% | 激进发布，可以大胆变更 |
| 25%-50% | 正常发布节奏 |
| 50%-75% | 谨慎发布，减少发布频率 |
| 75%-100% | 停止发布，只允许修复性变更 |
| > 100% | 错误预算耗尽，需要复盘改进 |

### 错误预算决策案例

假设推理服务 SLO 为 99.9%，每月错误预算约 43 分钟。本月已经过了 10 天，已经发生了两次故障，累计不可用 35 分钟。

此时错误预算消耗比例约为 35/43 = 81%。按照决策表，团队应该停止新功能发布，只允许修复性变更。同时分析这两次故障是否由近期变更引入，如果是，优先回滚或修复。

错误预算用完不是停业务，而是停止发布。业务继续运行，但团队精力转向稳定性改进。

对于训练任务，可以定义任务完成率 SLO。例如 95% 完成率意味着每 100 个任务允许 5 个失败。如果某月失败数超过 5 个，就需要排查是硬件问题、网络问题还是调度问题。

### 错误预算 Burn Rate

Burn Rate 衡量错误预算消耗速度。如果错误预算在很短时间内快速消耗，说明系统存在严重问题。

例如 SLO 是 99.9%，错误预算是每月 43 分钟。如果一次故障就消耗了 30 分钟，Burn Rate 很高。此时即使错误预算还没用完，也应该暂停发布，排查根因。

Prometheus 可以用 Burn Rate 告警规则：

```yaml
- alert: SLOBurnRateHigh
  expr: |
    (
      job:slo_errors_per_request:ratio_rate5m > (14.4 * 0.001)
      and
      job:slo_errors_per_request:ratio_rate1h > (14.4 * 0.001)
    )
  annotations:
    summary: "SLO 错误预算 1 小时内消耗超 2%，冻结发布"
```

这个规则的意思是：如果 5 分钟和 1 小时窗口内的错误率都超过 14.4 倍于 SLO 允许的错误率，说明 Burn Rate 过高，应该冻结发布。

## 6.5 变更管理三要素

变更是生产环境不稳定的主要来源。SRE 对变更管理的要求是"可控可逆"，每次变更都要回答三个问题：谁批的、什么时候做的、出了事怎么回。

![图02-变更管理三要素](images/ch06/图02-变更管理三要素.png)
*图 6-2：变更管理三要素*

三要素：

**变更审批**：不同级别变更走不同审批。常规变更至少提前 1 个工作日提交；紧急变更可简化审批，但事后必须补齐文档。

**变更窗口**：把变更影响收敛到低峰时段。核心业务变更通常在凌晨执行，窗口结束前必须完成验证或回滚。

**回滚预案**：变更前必须写好回滚步骤，包括回滚条件、回滚操作、回滚验证、回滚时限。命令必须预先写好，禁止现场组装。

变更按风险分级：

| 变更类型 | 审批级别 |
|----------|----------|
| 紧急变更 | 简化审批 |
| 常规变更 | 标准审批 |
| 性能优化变更 | 标准审批，需提供基线和目标 |
| 客户需求变更 | 标准审批，需需求确认函 |
| 跨部门协作变更 | 标准审批，需协作部门需求文档 |

审批层级通常是：申请人 → 一级审批 → 二级 SRE 团队负责人 → 值班 SRE 执行。

回滚预案模板：

```bash
# 回滚条件：推理服务 P99 延迟 > 500ms 持续 3 分钟，或错误率 > 1%
# 回滚操作：
helm rollback inference-svc 23 --namespace serving
# 回滚验证：
kubectl rollout status deployment/inference-svc -n serving
curl -s http://inference-svc:8080/healthz
# 回滚时限：5 分钟内未恢复 → 升级 SEV1 事故
```

### 变更操作文档要求

每份变更操作文档必须包含需求来源、需求描述、需求背景。操作步骤分四部分：备份、执行、验证、回滚。

备份步骤要明确备份操作、备份命令、备份验证。执行步骤要明确具体操作、执行命令、执行记录。验证步骤要明确验证操作、验证命令、验证标准。回滚步骤要明确回滚条件、回滚操作、回滚命令、回滚验证。

所有命令必须预先写好，禁止现场组装。危险命令如 rm、shutdown、reboot 要标注风险。命令必须包含完整参数，禁止使用未定义变量。

### 灰度验证要求

变更操作尽可能支持灰度验证。先在测试或预发环境验证，再推广到生产环境。分批次执行，观察无异常后再继续。

常见灰度方式：配置文件变更先更新 1 台节点验证；服务重启滚动进行，观察服务指标；脚本工具变更小流量验证，观察日志。

### 变更案例：推理服务配置更新

某次变更要调整推理服务的 batch size 以提升吞吐。变更方案：凌晨 2 点窗口执行，先灰度 1 个副本，观察 10 分钟 P99 延迟和错误率。如果正常，再滚动更新剩余副本。回滚条件：P99 延迟超过 500ms 或错误率超过 1%。

变更执行后，灰度副本指标正常，滚动更新到 50% 时发现 P99 延迟上升。触发回滚条件，立即回滚到上一个 Helm revision。回滚后服务恢复，次日做 Postmortem 分析 batch size 与延迟的关系。这个案例说明回滚预案和变更窗口的重要性。

## 6.6 发布策略

发布策略决定新版本如何安全接替旧版本。

**滚动更新**：K8s Deployment 默认策略。逐个替换 Pod，先启新 Pod，ready 后再杀旧 Pod。零停机的前提是配置了 readiness probe 和 maxUnavailable=0。

**蓝绿部署**：准备两套环境，新版验证通过后一次性切流量。优点是切换快、回滚快；缺点是需要双倍资源。

**金丝雀发布**：先放 1%-5% 流量到新版，观察核心指标。无异常再扩大。适合验证新版稳定性。

**灰度发布**：在金丝雀验证通过后，按比例渐进放量，如 10%→30%→50%→100%。强调的是放量节奏。

### 发布策略详细对比

| 策略 | 资源开销 | 流量切换 | 回滚速度 | 适用场景 |
|------|----------|----------|----------|----------|
| 蓝绿 | 2 倍 | 一次性全切 | 最快 | 资源充足、需快速回滚 |
| 金丝雀 | 1.x 倍 | 1%-5% 验证 | 快 | 高风险变更、需验证 |
| 灰度 | 1.x 倍 | 分档渐进放量 | 中 | 大规模用户、需观察 |
| 滚动 | 1+maxSurge | 逐 Pod 替换 | 中 | 常规迭代、K8s 原生 |

训练平台常用滚动更新和灰度发布。推理服务对延迟敏感，金丝雀和灰度更常用。

滚动更新说零停机但实际断了，通常是因为没配 readiness probe，或 maxUnavailable 设大了。没有 readiness probe，新 Pod 一启动就接流量，但服务还没 ready，导致 502。maxUnavailable 大于 0 意味着滚动期间允许可用 Pod 数减少，可能跌破容量底线。

蓝绿部署适合资源充足、需要秒级回滚的场景。推理服务这种对可用性敏感的核心服务，蓝绿部署的快速切回能力很有价值。但双倍资源成本需要提前规划。

金丝雀不是灰度，两者有区别。金丝雀是小流量验证阶段，回答敢不敢上。灰度是验证通过后的渐进放量阶段，回答怎么上。把两者混为一谈会跳过验证直接放量，或验证后一次性全切。

### 发布策略组合

实际生产中，几种发布策略经常组合使用。

**金丝雀 + 灰度**：先用 1%-5% 流量验证新版，无异常后按 10%→30%→50%→100% 渐进放量。Argo Rollouts 的 canary steps 就是典型实现。

**蓝绿 + 金丝雀**：在绿环境部署新版，先对绿环境放 1% 流量验证，验证通过后一次性把全部流量从蓝切到绿。结合了两者的优点。

**滚动 + 灰度**：K8s Deployment 默认滚动更新，但配合 Ingress 流量切分，可以在滚动过程中逐步调整新旧版本流量比例。

### 回滚机制

回滚是变更管理的最后防线。回滚机制按粒度分三层：

**GitOps 回滚**：Argo CD 以 Git 仓库为唯一事实来源。回滚可以让 Git 回到历史 commit，Argo CD 自动 sync。推荐用 `git revert` 产生新 commit，保留历史可追溯。紧急时也可用 `argocd app rollback`，但事后必须补 commit 对齐 Git。

**Helm rollback**：`helm rollback <release> <revision>` 回退到历史 revision。适合用 Helm 管理的应用。

**镜像版本回退**：直接把 Deployment 的 image tag 改回历史版本。适合只改了镜像没改配置的场景。

回滚的前提是镜像 tag 不可变。如果 tag 是 latest，回滚会拉到当前最新镜像，失去回滚意义。yunyun 的镜像 Tag 规则是分支加 commit 前 7 位加日期，保证每个 tag 唯一对应一个构建。

变更越频繁，越需要 SLO 保障。这听起来矛盾，但 SLO 的错误预算给变更提供了"安全额度"。错误预算充足时可以激进发布，错误预算消耗快时停止发布。没有 SLO 的频繁变更是赌博，有 SLO 的频繁变更是工程。

## 6.7 智算中心的特殊变更风险

智算中心的变更有一些特殊风险点。

**网络变更**：PFC、ECN、路由、BGP 的调整可能影响整网 RDMA 通信。这类变更必须走严格的变更窗口，且要提前在测试环境验证。PFC 和 ECN 主要在交换机端配置，服务器端只做 sysctl 调优。

**固件/驱动变更**：GPU 固件、网卡固件、CUDA 驱动升级可能导致训练任务异常。升级前需要评估影响范围，准备回滚方案。建议先在小批量节点验证，再推广到全集群。

**调度器配置变更**：Volcano 队列权重、抢占策略的调整会影响多租户公平性。需要小范围验证后再推广。错误的队列配置可能导致某些团队长期拿不到资源。

**存储变更**：并行文件系统、对象存储的扩容或升级，可能影响训练数据加载。需要评估 data_time 变化。存储升级通常影响面大，要安排在低峰窗口。

**GPU 节点变更**：新增或下线 GPU 节点会影响集群容量。节点上线前需要验证 Device Plugin、RDMA 网卡、存储挂载是否正常。节点下线前需要先 drain Pod，避免训练任务被强制中断。

**CUDA 驱动变更**：驱动升级可能影响现有训练镜像的兼容性。升级前要在测试节点验证主流训练框架是否能正常运行。建议保留旧版本驱动节点一段时间，让用户逐步迁移。

**固件/驱动回滚**：GPU 或网卡固件升级失败时，回滚可能需要进入维护模式。升级前必须确认回滚固件版本可用，并准备带外管理访问。

### 智算中心变更审批特殊要求

智算中心的变更通常按影响范围和风险等级分级。高风险变更如网络拓扑调整、核心交换机配置、存储扩容，需要跨团队评审。变更窗口通常安排在周末凌晨，避开训练任务高峰期。

变更执行时必须有双人复核。一人执行，一人确认。变更文档必须提前一天发出，让相关团队有时间准备应急预案。

回滚方案必须在变更前验证。对于不可逆操作，如数据库 schema 变更，要明确标注只能前滚修复，不能回滚。前滚修复需要准备修复脚本和验证步骤。

## 6.8 Postmortem 文化

故障发生后，SRE 强调写 Postmortem，中文常叫"事故复盘"。

好的 Postmortem 不追究个人责任，而是关注系统和流程改进。它通常包含：

- 故障时间线
- 影响范围
- 根因分析
- 触发因素
- 恢复过程
- 后续改进项

改进项要有明确负责人和完成时间。Postmortem 不是为了问责，而是为了防止同类问题再次发生。如果 Postmortem 变成追责大会，工程师会隐瞒信息，反而阻碍改进。

Postmortem 应该定期 review。每个月回顾一次近期 Postmortem，检查改进项是否按时完成，是否有重复发生的故障模式。重复发生说明改进没有到位。

### Postmortem 模板示例

一份好的 Postmortem 可以这样写：

**概述**：某月某日，推理服务出现 15 分钟不可用，影响在线业务。

**时间线**：
- 02:00 变更窗口开始，升级推理服务镜像
- 02:05 金丝雀 5% 流量异常，P99 延迟上升
- 02:08 触发回滚条件，执行回滚
- 02:15 服务恢复

**影响范围**：推理服务可用性下降，约影响 5% 请求。

**根因分析**：新版镜像中某个依赖库版本不兼容，导致特定输入下推理超时。

**触发因素**：金丝雀流量恰好没有覆盖到异常输入模式。

**恢复过程**：回滚到旧版本后服务恢复。

**后续改进**：
1. 金丝雀测试增加异常输入用例（负责人：张三，完成时间：下周）
2. 完善依赖版本兼容性检查（负责人：李四，完成时间：两周内）
3. 增加推理服务超时告警（负责人：王五，完成时间：本周）

## 6.9 这一环在整个链路中的位置

SRE 和变更规范贯穿整个 AI Infra 链路。

向上，它为平台用户和训练任务提供稳定性保障。用户不关心底层发生了什么，只关心任务能不能跑、推理服务可不可用。

向下，它需要基础设施团队、网络团队、平台开发团队协同。变更管理不只是运维团队的事，所有对生产环境的改动都需要纳入管理。

SRE 让系统从"有人修"变成"不易坏"。它是连接技术和业务的桥梁。在 AI Infra 这种高复杂度、高故障率、高影响面的场景，SRE 方法不是可选项，而是必需品。建立 SRE 体系需要从上到下的支持和长期的工程投入。

## 小结

SRE 是用软件工程方法解决运维问题，不是高级运维。它通过消除 Toil、量化可靠性、管理变更风险、建设可观测性，让系统整体更稳定。SLI、SLO、SLA 把可靠性量化，错误预算驱动发布节奏，黄金信号指导可观测性建设，变更管理三要素保证变更可控可逆，发布策略降低新版本风险，Postmortem 推动持续改进。在智算中心，网络、固件、驱动、调度器、存储变更有特殊风险，需要额外谨慎。SRE 文化需要团队长期坚持，不是一次项目就能建成。
