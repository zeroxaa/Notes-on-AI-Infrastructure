# 第 8 章 训练任务调优与排障

## 引子：训练慢，不一定是谁的锅

大模型训练出问题，第一反应往往是"网络又挂了"。但经过多年的排障实践，环境问题才是最常见的罪魁祸首。驱动版本不对、CUDA 没装好、镜像缺依赖，这些看起来基础的问题，经常让一屋子高级工程师查上几个小时。

训练调优和排障不是单纯的技术活，它有清晰的优先级和流程。按优先级查，能少走弯路。本章讨论如何定位训练中的性能瓶颈和常见故障。

需要强调的是，训练烧的是真金白银。以每卡时租 25 元人民币为例（实际租赁价格随市场和时段波动），8000 张 H200、一个 step 15 秒、训练 10000 步，总成本约 8000×25×(15×10000÷3600) ≈ 833 万元人民币（按 1 美元≈7.2 人民币估算，约 116 万美元）。因此，训练调优不只是技术优化，更是费用优化。每个百分点的效率提升，都直接对应真金白银。

另一个关键认知是：排障要有优先级。NCCL timeout 时先查网络，可能花两小时没结果，实际只是驱动版本不对。按环境→网络→存储→框架的顺序查，可以把定位时间从小时级压缩到分钟级。这个优先级不是理论推导，是生产事故的教训总结。

## 8.1 训练性能的关键指标

判断训练是否健康，先看几个核心指标。

**step_time**：训练每步的耗时。它由前向计算、反向计算、梯度同步、数据加载、优化器更新等部分组成。可以拆解为：

```
step_time = data_time + forward_time + backward_time + sync_time + optimizer_time
```

其中 sync_time 是梯度同步时间，主要由 AllReduce 决定。optimizer_time 是优化器更新参数的时间，通常占比很小。

训练调优的第一步，就是把 step_time 拆成这几项，看哪一项占主导。不同瓶颈对应不同优化方向，不能一刀切。

**data_time**：数据加载耗时。如果 data_time 占比高，说明 GPU 在等数据，瓶颈在存储或数据预处理。

**GPU 利用率**：DCGM 上报的 SM 活跃占比。持续低于 70% 通常有问题。

**MFU（Model FLOPs Utilization）**：模型实际算力利用率。大模型训练中，35%-60% 属于正常范围。

**tokens/s**：每秒处理的 token 数，直接反映训练吞吐。计算公式为：

```
单步 tokens = batch_size × seq_len × world_size × accumulation_steps
tokens/s = 单步 tokens / step_time
```

这个指标把模型规模、并行策略、数据格式都统一成一个数字，是汇报训练效率时最常用的指标。

**MFU（Model FLOPs Utilization）**：模型实际算力利用率。计算公式为：

```
MFU = (模型理论 FLOPs × 吞吐) / 卡峰值 FLOPs
```

大模型训练中，35%-60% 属于正常范围。低于 20% 说明浪费严重。在 8000 卡集群上，1% 的 MFU 差距可能对应数万元到数十万元人民币的成本差异（与训练总步数成正比）。

**loss 曲线**：训练健康的主要信号。正常应该缓慢下降；停滞、跳高、NaN 都说明有问题。

常见 loss 病态有四种：

- **正常健康**：缓慢下降，工程实践中常把每千步相对降幅 5%-10% 作为参考区间 [业界常见看法]
- **停滞高危**：在较高值停滞超过 1000 步，可能是学习率过高或数据失衡
- **突然跳高**：从 2.0 跳到 5.0 一步，可能是学习率爆炸、坏 batch 或梯度爆炸
- **NaN**：不可恢复，需要回滚 checkpoint

pretrain 的 loss 通常从 10 左右跌到 3-4 需要 500-2000 步；SFT 的 loss 从 4 跌到 0.5-1.5 需要几百步。

**grad_norm**：全局梯度范数。0.1-1.5 是常态，超过 2.0 要警惕梯度爆炸。

这些指标需要集中展示。wandb、swanlab、Grafana 都是常用工具。

### DCGM 核心指标

GPU 节点必须运行 DCGM Exporter，这是一切稳定训练的前提。DCGM 上报的核心指标包括：

- DCGM_FI_DEV_GPU_UTIL：SM 利用率，0-100%
- DCGM_FI_DEV_MEM_COPY_UTIL：显存复制活动占比
- DCGM_FI_DEV_GPU_TEMP：GPU 温度，70℃ 正常，80℃ 警惕
- DCGM_FI_DEV_POWER_USAGE：功耗，H200 满载约 700W，训练任务接近 TDP 是常态

GPU util 的读法需要结合实际场景：

- 全程低于 70%：优先查数据流水线
- 波动 0-100%：可能是通信脉动，查 step_time 是否稳定
- 70-85%：多数 DDP/FSDP 并行的正常区间
- 接近 100% 但 step_time 很长：可能是算力空转或通信等待

### 指标联合解读

单个指标往往不能说明问题，需要联合起来看。

GPU util 低于 70%，首先要怀疑数据流水线。GPU 在等数据时，计算单元自然空闲。如果 data_time 占 step_time 的 50% 以上，基本可以确定是数据加载瓶颈。

step_time 稳定但 loss 不下降，问题可能在超参数或数据质量。此时要看 lr、grad_norm、warmup 是否配置合理，以及数据是否有坏样本。

loss 突然跳高同时 grad_norm 超过 2.0，通常是学习率过大或遇到坏 batch。如果 grad_norm 被 clip 后仍不稳定，需要降低学习率或检查数据。

MFU 低但 GPU util 高，说明算力在空转。可能是通信同步间隙大、kernel 效率低，或者模型并行策略选择不当。

**lr 与 scheduler**：学习率决定参数更新步子大小，scheduler 决定学习率随时间怎么变。minimind 64M 模型用 lr=5e-4、0.1 保底 cosine。大模型通常需要更小的峰值学习率和更长的 warmup。

**warmup**：训练初期学习率从 0 逐渐上升到峰值，避免早期梯度爆炸。warmup 步数通常占总步数的 1%-3%。没有 warmup 直接上高学习率，很容易导致 loss spike 或 NaN。

## 8.2 数据流水线优化

数据加载慢是最常见的性能瓶颈。优化方法包括：

- 增加 DataLoader 的 num_workers
- 使用更高效的数据格式，如 WebDataset、TFRecord、Arrow
- 把数据预处理放到 CPU 并行完成
- 使用对象存储或本地高速缓存，减少远程读取

GPU 利用率持续低于 70%，首先要怀疑数据流水线。

数据流水线的目标是让 GPU 始终有数据可算。任何让 GPU 等待的环节都是瓶颈。常见瓶颈包括：远程存储读取慢、tokenizer 在线处理慢、数据预处理太重、num_workers 不够。

### 常见优化细节

**num_workers 设置**：通常设为 CPU 核数的 1/2 到 2/3。太少则 CPU 预处理跟不上 GPU，太多则进程间切换开销增加。在 K8s 环境中，还要注意 Pod 的 CPU limit 是否足够。

**数据格式选择**：小文件多会严重拖慢存储 IOPS。把数据打包成 WebDataset、LMDB 或 TFRecord 后，每次读取是顺序大 IO，效率显著提升。

**预 tokenize**：如果 tokenizer 在训练时在线运行，CPU 开销可能很大。预先把文本 tokenize 好并存成二进制格式，可以把训练时的 CPU 压力降到最低。

**预处理位置**：数据预处理应该在 DataLoader 的 worker 进程里完成，而不是在主进程。主进程还要负责 GPU 通信协调，预处理太重会抢 CPU 时间。

**缓存策略**：训练数据通常会被多次读取。利用本地 NVMe SSD 或分布式缓存，把热数据放在离 GPU 近的地方，可以减少远程存储访问。

**packing 优化**：大模型训练通常把多条短样本打包成一条长序列，减少 padding。padding 会降低有效 token 比例，浪费算力。好的 packing 策略可以显著提升 tokens/s 和 MFU。

**文件格式对比**：

| 格式 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 原始文本 | 直观易读 | 小文件多，IOPS 压力大 | 小规模实验 |
| WebDataset | 顺序大 IO，效率高 | 需要预处理 | 大规模训练 |
| LMDB | 随机读取快 | 构建成本高 | 需要随机访问 |
| TFRecord | 生态成熟 | 需要转格式 | TensorFlow/PyTorch 通用 |

### data_time 专项

data_time 是 DataLoader 从存储读取数据并做预处理的时间。它与通信无关，只与存储和 CPU 有关。

data_time 高的典型根因包括：存储带宽不足、num_workers 太少、数据集小文件太多、网络文件系统慢。排查时用 iostat 看存储 IO，用 top 看 CPU 利用率，用 DataLoader 配置调整做对照实验。

素材中特别提到一个经验阈值：data_time 大于 1500 秒时，几乎可以确定是存储问题，而不是通信或计算问题。

排查 data_time 高时，可以按这个顺序：先用 iostat 看存储带宽和 IOPS；再看 DataLoader 的 num_workers 和 CPU 利用率；然后检查数据集是否小文件过多；最后确认是否有远程读取瓶颈。

存储系统选择也影响 data_time：

| 存储 | 特点 | 适用场景 |
|------|------|----------|
| 本地 NVMe SSD | 速度快，容量有限 | 热数据缓存 |
| Lustre | 高并发并行文件系统 | 大规模训练 |
| JuiceFS | 对象存储之上的缓存层 | 多集群共享 |
| NFS | 简单但性能一般 | 小规模实验 |

大规模训练通常需要专门的并行文件系统，普通 NFS 很难满足 IOPS 和带宽需求。

### CPU 瓶颈

GPU 利用率低不一定是存储问题，也可能是 CPU 预处理跟不上。常见 CPU 瓶颈场景：

- K8s CPU limit 设置太低，比如只给 8 核，实际需要 32 核以上
- DataLoader num_workers 不够，CPU 预处理跟不上 GPU
- Tokenizer 在线运行，大规模训练时成为瓶颈
- 数据预处理在主进程执行，抢占 GPU 通信的 CPU 时间

排查时用 top 看 CPU 利用率，用 cat /sys/fs/cgroup/cpu/cpu.stat 看是否被 cgroup 限流，用 vmstat 看是否有 swap。

K8s 场景中，建议给训练 Pod 分配充足 CPU，或者去掉 CPU limit，只保留 request。CPU throttling 会让数据预处理变慢，直接拖累 GPU。

有时候 data_time 不是一开始就高，而是随训练时间逐步增长。这种情况可能是内存泄漏、缓存失效或页回收问题，需要结合 vmstat 和内存监控分析。

## 8.3 混合精度训练原理

混合精度训练用 fp16 或 bf16 代替 fp32 计算激活和梯度，可以显著降低显存占用并提升计算吞吐。

**fp16**：16 位浮点，指数位 5 位，尾数位 10 位。动态范围小，容易出现梯度下溢。

**bf16**：16 位浮点，指数位 8 位，尾数位 7 位。动态范围与 fp32 相同，但精度较低。在 NVIDIA Ampere 及以后架构上支持较好。

### Loss Scaling

fp16 训练中，梯度值可能小到 fp16 无法表示，导致梯度变成 0，模型停止更新。解决方法是 Loss Scaling：前向传播时把 loss 乘以一个较大的 scale，反向传播时梯度也会同比例放大，避免下溢；更新参数前再把梯度缩放回原始比例。

如果 scale 长期不增长或频繁回退，说明训练不稳定，需要降低学习率或检查数据。

### bf16 与 fp16 的选择

bf16 不需要 Loss Scaling，因为动态范围足够大。但它的精度比 fp16 低，对某些模型可能影响收敛。现代大模型训练越来越多采用 bf16，因为它更稳定，且对基础设施要求相对简单。

混合精度训练不是简单的"开开关"，需要框架、CUDA kernel、通信库共同支持。NCCL 也支持 fp16 和 bf16 的集合通信。

### 选择 fp16 还是 bf16

fp16 的优势是精度较高，但需要做 Loss Scaling，且对硬件支持要求更严格。bf16 的优势是稳定，不需要 Loss Scaling，但精度较低。

现代大模型训练越来越多采用 bf16，原因有三：一是 bf16 与 fp32 有相同的动态范围，不容易下溢；二是不需要调 Loss Scaling 参数，降低调参复杂度；三是 NVIDIA Ampere 及以后架构对 bf16 有很好的支持。

但对于某些对数值精度敏感的模型或算子，fp16 配合 Loss Scaling 可能是更好的选择。实际选择时需要做 ablation 验证。

### 学习率与 batch size 的关系

学习率和 batch size 通常正相关。batch size 翻倍时，学习率也可以适当提高。minimind 64M 模型的甜区是 lr=5e-4、batch=32。7B 大模型的学习率通常会降到 5e-5 量级。

warmup 步数通常占训练总步数的 1%-3%。大模型需要更长的 warmup 来稳定早期训练。配合 grad_clip=1.0 是常见的稳定训练组合。

### 精度异常排查

混合精度训练可能遇到的精度问题包括：bf16 AllReduce 精度不够、梯度累加溢出、ZeRO-3 参数汇聚精度损失。

排查时可以尝试：用 fp32 做 AllReduce、调整 loss scaling、关闭某些算子的 fp16/bf16 支持，或固定并行策略做对比实验。

## 8.4 环境一致性检查

部分 rank 能跑、部分 rank 报错，往往是环境不一致导致。常见表现包括 ImportError 只在某些节点、CUDA version mismatch、NCCL 版本不一致。

排查方法是用 ansible 批量检查所有节点：

```bash
ansible gpu_nodes -m shell -a "python --version"
ansible gpu_nodes -m shell -a "nvcc --version | grep release"
ansible gpu_nodes -m shell -a "python -c 'import torch; print(torch.cuda.nccl.version())'"
ansible gpu_nodes -m shell -a "nvidia-smi | grep 'Driver Version'"
```

K8s 场景下，还要确保所有 Pod 使用同一镜像。可以用 kubectl 查看所有 Pod 的 image 字段，应该只有一种。

版本兼容矩阵参考：H200 环境需要 NVIDIA 驱动 550+、CUDA 12.4+、NCCL 2.20+、PyTorch 2.3+、MLNX_OFED 24.04+。版本不匹配可能引发初始化失败、QP 异常、nccl-tests 校验失败等各种问题。

环境一致性是训练稳定的基础。上线前必须统一版本，并建立版本变更规范。

## 8.5 通信优化参数

通信优化包括：

- 使用 NCCL 最新稳定版
- 配置正确的 NCCL_IB_HCA 和 NCCL_NET_GDR_LEVEL
- 开启 GPUDirect RDMA
- 根据拓扑调整 NCCL_ALGO 和 NCCL_BUFFSIZE

### 关键参数说明

**NCCL_IB_HCA**：指定 NCCL 使用哪些 IB/RoCE 网卡。如果 NCCL 自动选择错误，比如选到了管理网卡，就需要显式设置。

**NCCL_NET_GDR_LEVEL**：控制 GPUDirect RDMA 的启用条件。设为 PHB 表示 GPU 与 NIC 在同一 PCIe Host Bridge 下才启用 GDR；设为 SYS 则允许跨 socket 使用 GDR，但性能通常较差。

**NCCL_ALGO**：强制指定 AllReduce 算法。小集群可用 RING，大规模跨机可用 TREE。一般不建议强制指定，让 NCCL 自动选择更合适。

**NCCL_BUFFSIZE**：通信缓冲区大小。大消息场景下适当增加可以提升吞吐，但会多占显存。

**NCCL_IB_TIMEOUT 与 NCCL_IB_RETRY_CNT**：大规模集群中，默认的 IB 超时可能太激进。1024 卡集群建议把 NCCL_IB_TIMEOUT 从默认 18 调到 22。但调大只是缓解，不能替代根因修复。

### 通信与计算重叠

PyTorch DDP 会把梯度按 bucket 切分，一个 bucket 的梯度计算完成后就立即启动 AllReduce，而不等所有梯度都算完。这样通信和反向计算可以重叠，减少纯等待时间。

如果通信时间占比过高，可以考虑增大 bucket size，让每次 AllReduce 传输更多数据，减少通信次数。但 bucket 太大也会延迟通信启动，影响重叠效果。

### 通信优化 checklist

调优通信前，建议按以下顺序检查：

1. 确认 NCCL 版本与 CUDA、驱动、固件兼容
2. 用 NCCL_DEBUG=INFO 确认网卡选择正确、GDR 生效、channel 数匹配
3. 用 nccl-tests 跑出单节点和多节点基线
4. 确认没有防火墙或 CNI 策略拦截 RDMA 端口
5. 在大规模集群中适当调整 NCCL_IB_TIMEOUT 和 NCCL_IB_RETRY_CNT

只有在硬件和配置都正确后，才考虑强制指定 NCCL_ALGO 或调整 NCCL_BUFFSIZE。

## 8.6 并行策略选择

根据模型规模和集群拓扑选择合适的并行策略。

- 模型能放进单卡显存：数据并行
- 模型太大：张量并行 + 流水线并行
- 序列很长：序列并行
- MoE 模型：专家并行

并行策略选择错误，会导致通信量过大或显存浪费。

**数据并行**：实现最简单，通信量等于模型梯度大小。适合单卡能放下完整模型的场景。

**张量并行**：把一层参数切到多张卡，通信频繁但单次量小。适合节点内，因为依赖 NVLink 高带宽。

**流水线并行**：按层切分模型，通信量小但有气泡。适合层数多的大模型。

**专家并行**：MoE 模型中把专家分散到不同卡，需要 AllToAll 交换 token。对网络 all-to-all 能力要求高。

### 选择策略的决策思路

选择并行策略时，先回答三个问题：

1. 单卡能不能放下完整模型？能，优先数据并行。
2. 模型太大，但层数多还是每层参数多？层数多用流水线并行，每层参数多用张量并行。
3. 序列长度是否超过阈值？序列很长时考虑序列并行。

实际训练中常常是多种策略组合。选择时要权衡显存、通信、计算三个维度。没有万能配置，需要根据模型和集群做 ablation。

## 8.7 Checkpoint 与保存策略

训练过程中定期保存 checkpoint 是基本操作，但保存策略设计不好也会成为瓶颈。

**常见错误**：所有 rank 各写一份 checkpoint。8000 卡场景下会产生 8000 份文件，造成存储 I/O 灾难。

**正确做法**：

- 只让 rank 0 写完整模型
- ZeRO-3 下用 DeepSpeed 原生保存，自动汇聚 shard 到 rank 0
- FSDP 下用 FullStateDictConfig 把参数 offload 到 CPU 再写磁盘

**异步保存**：为了不阻塞训练，可以先把状态转移到 CPU，再在后台线程写磁盘。训练继续下一个 step，等上一个保存完成后再触发下一个。

**存储空间**：checkpoint 文件通常很大。7B 模型 fp16 权重约 14GB，加上优化器状态和训练状态可能达到几十 GB。要提前规划存储容量，避免训练中途因磁盘满而失败。

## 8.8 排障优先级

训练出问题，排查顺序应该是：环境 → 网络 → 存储 → 框架参数。

*图 8-1：训练排障五层模型*

这个顺序不是拍脑袋定的。根据故障统计，环境问题约占 40%，网络问题约占 30%，存储约占 20%，框架参数约占 10%。从高概率往低概率查，效率最高。

五层排障模型：

| 层级 | 排查内容 | 常用工具 |
|------|---------|---------|
| 应用层 | 训练框架、超参数、数据 | 日志、loss 曲线 |
| K8s 层 | Pod 状态、调度、事件 | kubectl、事件日志 |
| 网络层 | IB/TCP、路由、防火墙 | ibstat、tcpdump |
| OS 层 | 内核、文件系统、驱动 | dmesg、sysctl |
| 硬件层 | GPU、网卡、内存 | nvidia-smi、ibstat |

## 8.9 常见故障及排查

### NCCL timeout

症状：训练卡住，日志出现 collective operation timeout。

![图02-NCCLtimeout排查流程](images/ch08/fig02-nccl-timeout.png)
*图 8-2：NCCL timeout 排查流程*

排查：

1. 开启 NCCL_DEBUG=INFO，看卡在哪一步
2. 用 nccl-tests 跑 AllReduce 基线，定位慢节点
3. 检查 ibstat，看网卡是否 Active、Rate 是否协商正确
4. 检查交换机端口误码和 discard
5. 检查路由、子网管理器、防火墙

典型 NCCL timeout 日志样例（已脱敏）：

```
[2026-04-20] [project] >> [rank23]: [Rank 2] Watchdog caught collective
operation timeout: WorkNCCL(SeqNum=28182, OpType=_REDUCE_SCATTER_BASE)
ran for 1800042 milliseconds before timing out.
```

这条日志说明某个 rank 在 ReduceScatter 阶段等待了约 1800 秒没有收到响应。下一步要找到卡住的 rank，再查它所在节点的网卡状态和带宽基线。

排查 NCCL timeout 的完整流程：

1. 打开 NCCL_DEBUG=INFO，找到 timeout 发生的 rank 和 channel
2. 用 nccl-tests all_reduce_perf 复现，看是否有固定 rank 慢
3. 对慢 rank 所在节点执行 ibstat，确认 State、Physical state、Rate
4. 用 ib_write_bw 做两两配对打流，定位低于基线的链路
5. ibping 验证连通性，排除单向路由问题
6. 检查 nvidia-smi 与 dmesg，排除 GPU 掉卡或 Xid 错误
7. 如果是 RoCE，检查 PFC/ECN 以及 iptables 放行情况
8. 必要时调整 NCCL_IB_TIMEOUT / NCCL_IB_RETRY_CNT，再观察是否复现

调大超时参数只是缓解症状，根因必须修复。否则问题会反复出现。

### Bootstrap 握手超时

症状：日志输出 master_addr 后卡住，没有后续。

排查：

1. 测试 master 端口连通性
2. 检查防火墙规则
3. 检查端口范围是否足够
4. 检查 conntrack 表是否满了

大规模集群中，conntrack 表满是一个常见原因。8000 卡场景下连接数巨大，默认 conntrack 上限很容易耗尽。临时修复可以调大 nf_conntrack_max。

Bootstrap 阶段超时的关键参数：

```bash
export NCCL_TIMEOUT=1800          # 默认 30min 对 8000 卡远远不够
export NCCL_BOOTSTRAP_TIMEOUT=300  # Bootstrap 阶段单独超时
```

如果日志只输出 `Bootstrap: Using master_addr=...` 后就停止，说明 rank 间握手失败。先测端口连通性，再查防火墙，最后查 conntrack。

### data_time 高

症状：step_time 中 data_time 占比大，GPU 利用率低。

排查：

1. 检查存储带宽是否足够
2. 检查 num_workers 是否太少
3. 检查数据预处理是否太重
4. 检查是否有远程读取瓶颈

素材中给出的经验是：data_time 超过 1500 秒，基本可以确定是存储问题，而不是通信或计算问题。

### OOM

症状：训练进程被 killed，或报 CUDA out of memory。

排查：

1. 减小 batch size
2. 开启梯度检查点
3. 使用 ZeRO 或 FSDP 切分优化器状态
4. 检查是否有内存泄漏

OOM 不一定是显存真的不够，也可能是分片策略配置错误。例如 8000 卡还用 ZeRO-1，每卡仍存完整参数，大模型必然 OOM。切换到 ZeRO-3 后，参数、梯度、优化器状态都分片，显存占用会大幅下降。

以 7B 模型 bf16 训练为例，显存占用估算：

- 参数：7B × 2 bytes = 14 GB
- 梯度：7B × 2 bytes = 14 GB
- 优化器状态：7B × 8 bytes = 56 GB
- 激活：取决于 batch_size 和 seq_len

ZeRO-1 下每卡存参数 + 梯度 + 优化器状态的一部分，约 28 GB。ZeRO-3 下理论上每卡只存 (14+14+56)/8000 ≈ 10.5 MB，实际有通信缓冲开销。

OOM 修复清单：

| 方案 | 节省量 | 代价 |
|------|--------|------|
| ZeRO-3 替代 ZeRO-1/2 | 参数+梯度也分片 | 通信量增加 |
| Activation Checkpointing | 激活显存降 60-80% | 计算量增加 30% |
| 减小 micro_batch_size | 线性减少激活 | 吞吐下降 |
| CPU Offload 优化器 | 优化器不占 GPU 显存 | 训练变慢 2-3x |
| 梯度累加大 batch | 不增显存提有效 batch | 单步时间不变，需更多 step |
| Flash Attention | 注意力激活显存 O(N²)→O(N) | 需要模型支持 |

### 显存泄漏

如果显存随 step 线性增长，很可能是显存泄漏。排查方法：

```python
if step % 50 == 0:
    torch.cuda.empty_cache()
    allocated = torch.cuda.memory_allocated() / 1e9
    print(f"Step {step}: allocated={allocated:.2f}GB")
```

如果 allocated 持续增长，用 torch.cuda.memory_summary() 查看分配栈，找到未释放的 tensor。常见原因是中间结果没有 detach、循环中累积了计算图、或某些回调保存了引用。

### loss 异常

症状：loss 不下降、跳高、出现 NaN。

排查：

1. 检查学习率是否过大
2. 检查数据是否有坏样本
3. 检查梯度裁剪是否配置
4. 检查混合精度是否导致下溢

如果 loss 突然变 NaN，通常无法现场抢救，应该回滚到上一个完整 checkpoint，降低学习率后重训。继续训练只会让损失更重。

grad_norm 超过 2.0 持续出现时，要先看是否伴随 loss 跳高。如果是，说明学习率或数据有问题；如果 loss 正常下降，可能是 clip 阈值设置偏保守。

### 数据质量

loss 异常有时是数据问题，不是超参数问题。坏样本、重复样本、格式错误的样本都可能导致 loss spike 或 NaN。

排查数据质量的方法：统计样本长度分布、检查是否有异常长样本、检查 token id 是否在词表范围内、抽样查看输出是否合理。

大模型训练的数据量通常很大，无法人工逐条检查。需要先定义质量指标，再用脚本批量扫描。常见的坏样本包括空文本、纯重复文本、编码错误文本。

### loss 与 grad_norm 联合分析

把 loss 和 grad_norm 放在同一个面板看，能发现更多问题：

- loss 不下降但 grad_norm 高：优化器被截断或遇到伪鞍点，可能是数据或初始化问题
- loss 快速下降但 grad_norm 攀升：学习率可能偏高，后面可能出现 spike
- loss 和 grad_norm 同时 spike：遇到坏 batch 或学习率过大
- loss 平稳但 grad_norm 接近 0：梯度消失，检查激活函数或深层网络连接

生产日志建议同时打印 clip 前和 clip 后的 grad_norm。clip 后是实际参与更新的梯度，clip 前是原始分布，两者结合才能判断训练稳定性。

## 8.10 大规模训练特有问题

从 16 卡扩展到 8000 卡，很多在小规模下可以忽略的问题会被放大。

### HF_MODULES_CACHE 竞争

使用 transformers 的 trust_remote_code 加载自定义 tokenizer 时，多个进程可能同时写入共享缓存目录，导致模块导入失败。错误通常表现为：

```
AttributeError: module 'transformers_modules...' has no attribute 'XXXTokenizer'
```

解决方法是让每个进程使用独立的缓存路径：

```bash
export HF_MODULES_CACHE=/tmp/hf_modules_${LOCAL_RANK}
```

在 4000 卡以上规模，还需要用 `--no-python` 启动包装脚本，确保环境变量在每个 Python 进程启动前生效。

### 初始化 broadcast 超时

大规模下，把模型参数从 rank 0 broadcast 到所有 rank 是单点扇出操作，容易超时。解决方法是各 rank 独立初始化权重，使用相同随机种子保证一致性，跳过 broadcast。

### 进程 import 耗时不同步

不同节点的 Python import 完成时间差异很大，有些进程已经进入 NCCL 初始化，有些还在 import transformers。这会导致 NCCL 集合通信建立不一致，部分进程卡在 `cxiWaitEventWait`。

解决方法是在 torchrun 之前做一次 Python import 预热，让所有大型包的 .py 文件进入文件系统缓存，后续并行 import 时耗时更均匀。

### ZeRO-3 通信量过大

8000 卡下 ZeRO-3 的参数 allgather/reduce-scatter 通信量极大，拓扑复杂度 O(n²)，可能导致 allreduce 卡死。解决方法是切换到 ZeRO-2，只分片优化器状态和梯度。

### 梯度归约为 0

某些训练配置中的 `convert_to_iter_based=True` 与 DeepSpeed 梯度累积机制存在交互问题，可能导致梯度归约结果为 0。去掉该选项后通常恢复正常。

### 逐级扩展测试

大规模训练不要一次性拉到 8000 卡。建议逐级扩展：8 卡单机 → 64 卡同 leaf → 256 卡跨 leaf → 1024 卡跨 spine → 4096 卡 → 8000 卡。

每一步通过标准：nccl-tests 带宽不低于基线 70%，无 timeout，无报错。不通过不扩。这种逐级验证可以把问题暴露在可控规模，避免全量启动后才发现问题。

### 最终配置固化

8000 卡训练的最终配置应该包括：启动脚本、包装脚本、训练入口 monkey-patch、DeepSpeed 配置、训练配置文件。所有参数和修复都要文档化，方便复现和交接。

### 代码死锁

症状：进程在但 GPU 利用率 0%，无 NCCL 报错，部分 rank 卡住。

最常见的原因是条件 barrier 或非对称集合操作。例如：

```python
# 错误：只有 rank 0 执行 barrier
if dist.get_rank() == 0:
    dist.barrier()

# 正确：所有 rank 都必须执行 barrier
dist.barrier()
```

模型保存只在 rank 0 执行且缺少 barrier，也会导致死锁。rank 0 保存 checkpoint 时，其他 rank 已进入下一个 step 的 all_reduce，结果 rank 0 超时。

排查方法包括：设置更短的分布式超时、用 faulthandler 打印调用栈、用 py-spy 附加卡住的进程。

### GPU 硬件故障

症状：nvidia-smi 报错、CUDA error、Xid 错误、dmesg 报错。

常见 Xid 错误：

- Xid 31：FIFO MMU 页错误，通常可恢复，偶发可忽略
- Xid 48：ECC 双比特错误，严重，检查显存健康
- Xid 79：GPU 掉线，严重，通常需换卡

排查时用 nvidia-smi 确认卡是否存在，用 dcgmi diag -r 3 做全面诊断，用 nvidia-smi -q -d ECC 查看 ECC 错误。uncorrected ECC 大于 0 的卡必须淘汰。

## 8.11 工具链

训练排障需要一套工具链。

**监控**：DCGM Exporter + Prometheus + Grafana，看 GPU、显存、功耗、温度。

**日志**：Loki 或 ELK，集中查看训练日志。

**通信测试**：nccl-tests、ibstat、ibping、ib_write_bw。

**性能剖析**：torch.profiler、Nsight Systems，看算子级耗时。

**训练面板**：wandb、swanlab、TensorBoard，跟踪 loss、lr、grad_norm。建议一个面板同时展示 loss、grad_norm、lr、tokens/s、data_time 五个核心指标，按 rank 拆分呈现。

### 工具使用层次

第一层是看面板。DCGM + Grafana 能解决 70% 的问题，比如 GPU 利用率低、温度过高、显存异常。

第二层是读日志。NCCL_DEBUG=INFO、训练框架日志、K8s 事件能提供更多上下文。

第三层是 profiler。torch.profiler 和 Nsight Systems 能看到算子级时间线，适合定位深层性能问题。但 profiler 开销大，不要长期开启。

### torch.profiler 用法

torch.profiler 可以快速定位耗时排名靠前的算子。典型用法：

```python
with torch.profiler.profile(
    activities=[torch.profiler.ProfilerActivity.CPU,
                torch.profiler.ProfilerActivity.CUDA],
    record_shapes=True,
    profile_memory=True,
) as prof:
    for step in range(10):
        train_step()

print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=20))
```

输出中 cuda_time_total 排名前几的算子，就是优化的重点。如果 AllReduce 或 ncclKernel 排名靠前，说明通信是瓶颈；如果 aten::copy_ 排名靠前，说明数据搬运多。

### Nsight Systems 用法

Nsight Systems 提供完整的时间线视图，适合分析跨 kernel、跨通信的同步 gap。采集命令：

```bash
nsys profile \
  --trace=cuda,nccl,nvtx,osrt \
  --gpuctxsw=true \
  --output=profile_rank0 \
  --force-overwrite=true \
  python train.py
```

Nsight 数据量大，只 profile 1-2 个节点即可，不要全量采集。

### 轻量计时替代

在不想开 profiler 时，可以在代码里手动计时：

```python
step_start = time.time()
t0 = time.time()
batch = next(dataloader)
data_time = time.time() - t0

t0 = time.time()
loss = model(batch)
loss.backward()
compute_time = time.time() - t0

t0 = time.time()
optimizer.step()
opt_time = time.time() - t0

step_time = time.time() - step_start
```

通过打印 data_time、compute_time、opt_time 的占比，可以快速定位瓶颈方向。

## 8.12 这一环在整个链路中的位置

训练调优与排障是 AI Infra 价值的最终体现之一。

向上，它直接决定模型训练能否按时完成、成本是否可控。训练任务跑不起来，前面的基础设施投入都白费。

向下，它依赖前面所有章节的内容：IDC 设计、网络稳定性、GPU 选型、调度平台、SRE 规范。任何一层出问题，都会在这里暴露。

训练排障要求工程师既有广度——从硬件到框架都要懂，又有深度——能根据现象快速定位层级。

调优和排障的本质，是用数据说话。没有监控就调参是盲飞，没有日志就定位是猜测。DCGM、wandb、NCCL_DEBUG、profiler 这些工具，是把主观感受变成客观证据的桥梁。

预训练与 SFT 的调优重点也有所不同。预训练更关注吞吐和 MFU，数据量大，对 loss 长期下降趋势要求高。SFT 数据量小，更关注收敛稳定性，容易过拟合，epochs 通常控制在 2-3 以内。

训练监控可以分成三个层级：指标面板 5 秒粒度、训练日志 100 步粒度、profiler 算子级粒度。70% 的问题看面板就能发现，25% 需要读日志，只有 5% 的真难题需要 profiler。日常先把面板和日志用好，不要一上来就抓 profiler。

训练调优没有银弹。每个模型、每个集群、每个数据集都有自己的特性。建立系统的排查流程和完整的监控体系，比记住几个参数更有价值。把每次排障的过程和结论记录下来，逐步形成团队知识库，是规模化运维的关键。知识库越厚，面对新问题时的判断就越快，团队的整体排障能力也会持续提升。

## 小结

训练调优的本质是用数据定位瓶颈。step_time 拆解为 data_time、compute_time 和 sync_time，GPU 利用率、MFU、loss 和 grad_norm 联合解读才能判断问题层级。排查顺序是环境 → 网络 → 存储 → 框架参数，大规模训练要逐级扩展验证。Checkpoint、混合精度、并行策略选择和工具链共同决定训练能否高效稳定完成。
