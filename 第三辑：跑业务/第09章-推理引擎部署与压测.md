# 第 9 章 推理引擎部署与压测

## 引子：训练是一次性投入，推理是长期运营

训练大模型很花钱，但训练完成后，模型还要持续对外提供服务。推理的成本和体验，决定了一个模型能不能真正落地。

与训练不同，推理更关注延迟和吞吐量。用户希望第一个字尽快出现，后续生成流畅；平台希望同一块 GPU 能服务更多用户。这两个目标经常冲突，需要推理引擎在中间做精细平衡。

训练是"一次性投入"：算力、电力、时间花出去，换回一组模型权重。推理是"长期运营"：模型上线后，每处理一个 token 都要消耗 GPU 算力、显存带宽和电力。一个日活百万的 AI 应用，每天可能产生数十亿次 token 调用。推理成本会随调用量线性增长，最终可能超过训练成本。

因此，推理阶段的优化方向不是"跑得快"这么简单。它要追求单位成本下服务更多用户，同时保证用户体验。这要求工程师同时理解模型结构、GPU 特性、推理引擎机制和分布式部署。

本章讨论主流推理引擎的选择、部署要点和压测方法。我们会把重点放在工程落地层面。包括：怎么根据业务特征选引擎，怎么配参数，怎么验证性能，怎么写一份能指导上线的压测报告。

## 9.1 推理与训练的本质差异

训练是一次性的大规模计算，目标是让模型学到参数。推理是反复调用模型做预测，目标是在有限资源下快速响应请求。

训练的任务特征是：batch 大、序列长度固定、目标是让 loss 下降。工程师关注的是吞吐量、GPU 利用率和训练稳定性。一次训练可能持续数天到数周，期间 GPU 被独占使用。

推理的任务特征是：请求小、序列长度动态变化、目标是快速返回结果。工程师关注的是延迟、并发数和成本。推理服务需要 7×24 小时运行，多个用户共享同一块 GPU。

这种差异决定了优化方法完全不同。训练可以用大 batch 提高算力利用率，推理则要在小 batch 甚至单请求时保证低延迟。训练可以容忍偶尔的重启，推理服务中断直接影响用户。

| 维度 | 训练 | 推理 |
|------|------|------|
| 目标 | 学习参数 | 使用参数预测 |
| 批次 | 大，固定长度 | 小，动态长度 |
| 运行时长 | 数天到数周 | 持续运行 |
| 优化重点 | 吞吐量 | 延迟 + 吞吐量 |
| 资源模式 | 独占式 | 共享式 |

推理采用自回归生成：每次生成一个 token，再把新 token 加入输入，继续预测下一个。这个过程需要维护 KV Cache，记录之前所有 token 的 Key 和 Value 向量。

随着序列变长，KV Cache 会占用大量显存。对于长上下文，KV Cache 可能成为显存的主要消耗者。理解这一点，是后续所有优化决策的前提。

## 9.2 推理性能的核心指标

评估推理服务，通常看以下指标。

**TTFT（Time To First Token）**：从请求发出到收到第一个输出 token 的时间。主要由 Prefill 阶段决定，影响用户"多久看到响应"。

**TPOT（Time Per Output Token）**：生成阶段每两个 token 之间的平均间隔。主要由 Decode 阶段决定，影响生成流畅度。

**ITL（Inter-Token Latency）**：相邻两个输出 token 之间的时间间隔。与 TPOT 类似，但更强调稳定性。ITL 抖动大会让用户感知到卡顿。

**吞吐量**：每秒处理的 token 数或每秒完成的请求数。反映 GPU 利用效率。

**并发数**：系统同时处理的请求数量。

**显存使用**：KV Cache、模型权重、激活值共同占用显存。

这些指标不是孤立的。提高并发通常会增加 TTFT 和 TPOT，降低延迟则会减少并发。调优的核心就是找到业务可接受的平衡点。

## 9.2.1 Prefill 与 Decode 的计算特征

大模型推理分为 Prefill 和 Decode 两个阶段。它们的计算特征截然不同，优化方向也不同。

**Prefill 是计算密集型（compute-bound）**。

Prefill 阶段一次性处理整个 prompt。核心运算是注意力计算和 FFN 前向传播。当 prompt 较长时，矩阵乘法的算术强度很高。以 Llama-2-7B 为例，prompt 长度为 2048 时，Prefill 的算术强度约为 2048 FLOPs/Byte，远高于 H200 的算力带宽比拐点（按 BF16 峰值 1979 TFLOPS / 4.8 TB/s 计，约 412 FLOPs/Byte，含稀疏性）。因此 Prefill 受限于 GPU 算力，MFU 可达 60%–80%。

**Decode 是访存密集型（memory-bound）**。

Decode 阶段每次只处理一个新 token。FFN 层的矩阵乘法变成 [1, hidden_size] × [hidden_size, intermediate_size]。读取的权重矩阵大小不变，但计算量大幅减少。算术强度约为 1 FLOP/Byte，远低于拐点。因此 Decode 阶段 GPU 大部分时间花在读取权重和 KV Cache 上，计算单元大量闲置。

这个差异有一个重要推论。在 Decode 阶段，把多个请求拼成 batch 同时计算，可以共用一次权重读取。这样能让闲置算力服务更多请求。这就是批处理和连续批处理的根本价值。

| 维度 | Prefill | Decode |
|------|---------|--------|
| 每步处理 token 数 | N（整个 prompt） | 1 |
| 核心矩阵乘法 | [N, d] × [d, d] | [1, d] × [d, d] |
| 算术强度（7B 模型） | 约 2048 FLOPs/Byte | 约 1 FLOP/Byte |
| 瓶颈类型 | compute-bound | memory-bound |
| GPU MFU（batch=1） | 60%–80% | 5%–15% |

## 9.3 推理的两个阶段

大模型推理分为 Prefill 和 Decode 两个阶段。

![图01-Prefill与Decode](图片/第09章/图01-Prefill与Decode.png)
*图 9-1：大模型推理的两个阶段*

**Prefill**：一次性处理整个 prompt，为每个 token 计算 K 和 V，存入 KV Cache，最后输出第一个 token。这个阶段计算量大，属于 compute-bound。

**Decode**：基于已有上下文，每次生成一个 token，并把新 token 的 K 和 V 追加到 KV Cache。这个阶段每次只处理一个 token，但要把模型权重全部读入，属于 memory-bound。

两个阶段特性不同，优化方向也不同。同时，这两个阶段共享同一个 GPU，混合调度时会互相抢占资源。一个长 prompt 的 Prefill 可能阻塞其他请求的 Decode，这是 Chunked Prefill 和 PD 分离技术出现的原因。

Prefill 优化方向：提高算力利用率、支持更长的 prompt、使用更高效的 attention kernel、通过张量并行分散计算。

Decode 优化方向：批处理多个请求、减少 KV Cache 显存占用、减少权重读取次数、使用 CUDA Graph 降低 kernel launch 开销。

## 9.3.1 KV Cache 的显存压力

KV Cache 是推理服务的核心显存消耗者。理解它占多少空间，才能判断一块 GPU 能同时服务多少请求。

单个 token 的 KV Cache 大小可以用以下公式估算：

```
KV per token = 2 × L × H_kv × d_head × b
```

其中 L 是模型层数，H_kv 是 KV 头数，d_head 是每个头的维度，b 是精度字节数（FP16 为 2，FP8 为 1）。

以 Llama-2-7B（FP16）为例：L=32，H_kv=32，d_head=128，b=2。单 token KV Cache = 2 × 32 × 32 × 128 × 2 = 524288 字节，约 0.5 MB。

一个序列长度为 4096 的请求，KV Cache = 4096 × 0.5 MB = 2 GB。如果同时服务 100 个这样的请求，KV Cache 总量 = 200 GB，超过一块 H200 的 141 GB 显存。

再看 Llama-2-70B（FP16，8 卡张量并行）：L=80，H_kv=8（GQA），d_head=128，b=2。单 token KV Cache = 2 × 80 × 8 × 128 × 2 = 327680 字节，约 0.3125 MB。序列长度 8192 时，单请求 KV Cache = 8192 × 0.3125 MB = 2.5 GB。100 个并发请求 = 250 GB。

GQA（Grouped-Query Attention）通过减少 KV 头数缓解了压力。如果 70B 模型不用 GQA，单 token KV Cache 会达到 2.5 MB，8192 长度的单请求 KV Cache 就是 20 GB，几乎无法高并发。

但即使用了 GQA，KV Cache 仍然是显存的主要消耗者。因为模型权重是固定的，而 KV Cache 随并发请求数量和序列长度动态增长。10 个请求还好，100 个请求就能吃光所有剩余显存。这也是 PagedAttention、KV Cache 量化、前缀缓存、PD 分离等技术存在的根本原因。

## 9.4 主流推理引擎

当前生产环境常用的推理引擎主要有 vLLM、TensorRT-LLM 和 SGLang。

### vLLM

vLLM 由伯克利 LMSYS 团队开源，核心创新是 PagedAttention。

![图02-PagedAttention分页](图片/第09章/图02-PagedAttention分页.png)
*图 9-2：传统连续分配 vs PagedAttention 分页*

它把 KV Cache 按固定大小分块管理。这种设计借鉴操作系统虚拟内存分页思想，能消除显存碎片，支持更高的并发。

vLLM 把 KV Cache 划分为固定大小的 Block（默认 block_size=16）。每个请求持有一张 Block Table，记录逻辑 Block 到物理 Block 的映射。物理 Block 可以分散在显存中，不需要连续。请求按需分配 Block，完成后立即释放回空闲池。

这种方式几乎消灭了外部碎片，内部碎片也极小（最后一个 Block 最多浪费 15 个 token 的空间）。vLLM 论文实测 KV Cache 显存利用率从传统方式的 20%–40% 提升到约 96%。

vLLM 还支持 CUDA Graph 优化。Decode 阶段每次 iteration 的计算量很小，kernel launch 开销可能成为瓶颈。CUDA Graph 把一系列 kernel 调用预先录制好，之后每次只需"播放"这个图，减少 CPU-GPU 交互开销。使用 CUDA Graph 后，Python 开销可以从 30%–40% 降到 5% 以下，吞吐量提升 1.5–2 倍。但 CUDA Graph 要求 batch 组成稳定，有新请求加入或退出时需要重新录制。

优势：
- 开源生态活跃，社区支持好
- PagedAttention 提升显存利用率和并发能力
- 支持连续批处理（continuous batching），每个 decode iteration 动态调整 batch，完成的请求立即退出，新请求立即加入
- 支持多种硬件和后端
- 与 OpenAI API 兼容，应用侧迁移成本低

连续批处理和 PagedAttention 是互相配合的。连续批处理要求每个 decode step 都能快速加入新请求，新请求需要立即分配 KV Cache 空间。PagedAttention 的 Block 可以分散存放，新请求只需从空闲 Block 池取几个 Block，不需要连续空间。两者配合才能实现高吞吐低延迟。

劣势：
- 某些新模型或量化格式的支持可能滞后
- 极致性能上不如 TensorRT-LLM
- 全 Python 架构在某些场景下不如全 C++ 引擎快

以 70B 级别模型在 8×H200 上运行 vLLM 为例，短 prompt 时 TTFT 通常在几十到一百毫秒量级，Prefill 吞吐可达每秒数千 tokens，Decode 吞吐通常在每秒一百到数百 tokens，具体数值随输入长度、并发数和调度参数变化较大。FP8 量化后，权重和 KV Cache 占用减半，Decode 吞吐通常优于 FP16，同时显存余量更充裕。生产部署前必须以真实 prompt 分布做压测，不能直接用理论值或社区参考值做容量规划。

### TensorRT-LLM

TensorRT-LLM 是 NVIDIA 推出的推理引擎，基于 TensorRT 构建，针对 NVIDIA GPU 做了深度优化。它的核心思路是把模型编译成 NVIDIA GPU 上的高效执行图，充分发挥 Tensor Core 和内存带宽。

优势：
- 在 NVIDIA GPU 上性能优秀，原始吞吐通常比 vLLM 高 10%–30%
- 支持多种量化格式（FP8、INT8、INT4），且有硬件级优化
- 与 NVIDIA 硬件生态集成好，能使用最新的 Hopper 架构特性

劣势：
- 只支持 NVIDIA GPU，无法在其他硬件上运行
- 闭源部分较多，黑盒程度高
- 新模型支持需要等待官方更新，社区贡献受限
- 需要 build engine，配置复杂，模型适配成本高
- 热更新和模型 reload 流程不如 vLLM 灵活

TensorRT-LLM 适合模型固定、追求极致性能的场景。如果业务需要频繁切换模型或快速支持新模型，vLLM 的灵活性更有优势。

### SGLang

SGLang 由伯克利开发，强调结构化生成和高效调度。它在某些场景下能提供比 vLLM 更高的吞吐，尤其在 Agent 多轮对话和结构化输出场景。

优势：
- 结构化生成能力强，JSON/regex 约束解码更快
- 调度效率高，RadixAttention 原生支持前缀缓存
- 适合复杂 prompts 和多轮对话
- 原生集成 Mooncake KV Cache 分层存储，支持 GPU HBM → Host DRAM → Mooncake DRAM → NVMe SSD → 3FS 五级温度分层
- 在长上下文场景下，通过 KV Cache offload 突破单卡显存限制

劣势：
- 生态相对较新
- 社区规模小于 vLLM
- 模型覆盖不如 vLLM 广
- 生产验证时间不如 vLLM 长

### 怎么选

选型取决于具体需求：

- 追求通用性和生态：选 vLLM
- 使用 NVIDIA GPU 且追求极致性能：选 TensorRT-LLM
- 需要结构化生成或复杂调度：考虑 SGLang
- 多硬件环境：vLLM 更灵活
- 长上下文/Agent 多轮对话场景：SGLang 的 KV Cache 分层存储有优势

下表从多个维度给出更直观的对比：

| 维度 | vLLM | TensorRT-LLM | SGLang |
|------|------|-------------|--------|
| 开发方 | 开源社区（UC Berkeley 发起） | NVIDIA | 伯克利 |
| KV Cache 管理 | PagedAttention（Block Table） | 专用内存管理 | RadixAttention（Radix Tree） |
| 模型支持 | 极广 | 需逐个适配 | 较广，增长快 |
| 易用性 | 高，pip install 即用 | 低，需 build engine | 中等 |
| 原始吞吐 | 高 | 通常更高 | 与 vLLM 同量级 |
| 结构化生成 | 支持 | 支持 | 核心优势 |
| 硬件支持 | NVIDIA/AMD/Intel/TPU/Gaudi | 仅 NVIDIA | 主要为 NVIDIA |
| 开源程度 | 完全开源 | 部分闭源 | 开源 |

## 9.5 部署要点

推理服务部署不只是把模型加载起来。需要同时考虑精度、并行、服务编排、扩缩容和长上下文等多个方面。

**模型格式**：根据需求选择 FP16、BF16、FP8、INT8、INT4 等精度。量化能降低显存占用和提高吞吐，但可能损失精度。

**并行策略**：
- 张量并行（TP）：把模型层内切分到多张 GPU，降低单卡显存压力
- 流水线并行（PP）：把模型按层切分，适合超长模型
- 数据并行（DP）：部署多个副本，提高整体吞吐

vLLM 的流水线并行支持不如张量并行成熟。在纯推理场景，大多数部署用 TP 就够了，因为推理不涉及梯度同步，TP 的通信开销比训练小。

**服务编排**：使用 KServe、Seldon、或自研网关做负载均衡、版本管理、灰度发布。

**扩缩容**：根据 QPS 和延迟自动扩容缩容。推理服务通常有昼夜波峰波谷，弹性很重要。

**长上下文优化**：使用 chunked prefill、前缀缓存、稀疏注意力等技术降低长序列成本。

**容量规划示例**：以 GLM-5.2 FP8 模型为例。该模型总参数量约 744B，FP8 量化后权重体积约 744 GB（1 字节/参数），TP=8 后每卡约 93 GB。GLM-5.2 采用 MLA，BF16 下每 token KV Cache 约 70 KB；128K 上下文单请求 KV Cache 约 9.2 GB。16 个请求的 KV Cache（BF16）约 150 GB，32 个请求约 294 GB；若启用 KV Cache FP8，上述数字可减半。加上激活与预留约 50 GB，8×H200 总 HBM 约 1.1 TB，因此 BF16 KV Cache 下约支持 16 路 128K 并发，FP8 KV Cache 下可支持约 30 路。这再次说明推理容量规划不能只看模型权重，必须同时算 KV Cache 和激活开销。

## 9.5.1 量化格式选择

量化是降低推理成本最直接的手段之一。不同格式适合不同场景。

| 方案 | 精度 | 显存减少 | 速度提升 | 精度损失 | 硬件要求 |
|------|------|---------|---------|---------|---------|
| FP16 | 16 位 | 基准 | 基准 | 0 | 通用 GPU |
| FP8 | 8 位 | 50% | 1.5–2 倍 | 小于 1% | H100/H200 |
| INT8（GPTQ） | 8 位 | 50% | 1.5–2 倍 | 1%–3% | A100 及以上 |
| INT4（AWQ） | 4 位 | 75% | 2–3 倍 | 2%–5% | A100 及以上 |
| INT4（GPTQ+Marlin） | 4 位 | 75% | 3–4 倍 | 2%–5% | A100 及以上 |

选择策略：

- H100/H200 且追求最高性能：FP8。H100/H200 的 Tensor Core 原生支持 FP8 矩阵乘法，不需要先反量化到 FP16 再算。权重体积减半，速度提升 1.5–2 倍，精度损失小于 1%。
- 显存极度受限且可接受少量精度损失：INT4 AWQ + Marlin。Marlin kernel 把反量化和矩阵乘法融合在一个 CUDA kernel 里，显存读写只有一次，速度显著快于标准 GPTQ kernel。
- A100 且需要量化：INT8 GPTQ。
- 精度优先：FP16，不量化。

除了权重量化，KV Cache 也可以量化。FP16 KV Cache 每元素 2 字节，FP8 每元素 1 字节，INT4 每元素 0.5 字节。KV Cache 量化不减小模型体积，但减小每个请求的 KV Cache 显存占用，直接提升并发能力。对于短序列（小于 2048 token），FP8 KV Cache 几乎没有精度影响；对于长序列（8K 以上），建议用 FP8 而非 INT4。

## 9.5.2 服务部署架构

推理服务上线后，需要考虑负载均衡、模型路由、灰度发布和回滚能力。常见方案有两类：KServe 等开源方案和自研网关。

**KServe** 是 Kubernetes 上常用的模型服务框架。它提供标准化的 InferenceService CRD，支持金丝雀发布、A/B 测试、自动扩缩容。优势是与 K8s 生态集成好，文档丰富；劣势是对于大模型推理的特殊需求需要额外开发。例如按模型名路由、按 prompt 长度路由、PD 分离路由等。

**自研网关** 适合有复杂路由策略的团队。常见功能包括：
- 按模型名称路由到不同推理副本
- 按 prompt 长度或预估生成长度做负载均衡
- 根据 P/D 队列峰值把请求分发到 Prefill 池或 Decode 池
- 灰度发布新模型版本，失败时自动回滚
- 限流、熔断、降级

按照本书项目 AGENTS.md 中的原则，**默认开源自建**。这不是因为开源方案总是最好，而是因为 AI Infra 变化快、定制需求多，闭源方案很难灵活调整。开源自建的优势在于可控性强、人才储备丰富、生态完整、避免厂商锁定。

无论用哪种方案，都需要保证模型加载完成后再接入流量。readiness probe 要在模型可 serving 时才把 Pod 纳入 Service，避免请求打到还没准备好的实例。

## 9.5.3 关键优化技术

部署推理服务时，有几项技术能显著改善延迟和吞吐。

**Chunked Prefill**：把长 prompt 切成多个 chunk，每个 decode iteration 处理一个 chunk，同时继续处理 Decode 请求。这样长 Prefill 不会阻塞整个 batch 的 Decode。例如一个 8000 token 的 prompt，不启用 Chunked Prefill 时会让 batch 中其他 Decode 请求停顿 40–80ms；启用后每个 chunk 只停顿 3–5ms。Chunked Prefill 在 vLLM v0.5.0 后默认启用。

**前缀缓存（Prefix Caching）**：对相同或相似前缀复用 KV Cache。RAG 和系统提示词场景收益明显。vLLM 的 Automatic Prefix Caching 会自动检测请求之间的公共前缀，缓存公共前缀的 KV Cache Block，后续请求直接复用。当所有请求使用同一段 system prompt 时，命中率可达 80%–95%，TTFT 降低 5–10 倍。

**PD 分离（Prefill-Decode Disaggregation）**：把 Prefill 和 Decode 放到不同实例上，分别优化资源配比。P 集群专门做 Prefill，GPU 算力打满；D 集群专门做 Decode，显存带宽打满。代价是 Prefill 产生的 KV Cache 需要从 P 节点传到 D 节点。以 Llama-2-70B FP16（无 GQA，单 token KV Cache 约 2.5 MB）为例，单请求 2048 token 的 KV Cache 约 5GB，100 并发就是 500GB，需要高带宽 RDMA 网络传输。PD 分离不是 vLLM 内置功能，而是建立在 vLLM 之上的架构模式。

**投机解码（Speculative Decoding）**：用小模型生成候选 token，大模型验证，加速 Decode。适合 Decode 是瓶颈的场景。但小模型草稿的接受率会影响实际收益，需要在具体模型上验证。

## 9.5.4 可观测性建设

推理服务上线后，需要持续监控以下指标：

- TTFT P50/P99：反映 Prefill 阶段健康度
- TPOT P50/P99：反映 Decode 阶段健康度
- Throughput（tokens/s 或 req/s）：反映 GPU 利用率
- 请求排队数（vLLM: num_requests_waiting）：反映容量是否充足
- GPU 利用率与显存使用：反映资源是否充分利用
- 前缀缓存命中率：反映前缀缓存效果
- 错误率与超时率：反映服务稳定性

这些指标应接入 Prometheus + Grafana，设置合理的告警阈值。例如 TTFT P99 超过 2 秒、TPOT P99 超过 100ms、排队数持续增长时，需要触发扩容或调优。

## 9.6 压测方法

上线前必须压测，不能只看单请求延迟。

**压测维度**：
- 不同并发数下的 TTFT 和 TPOT
- 不同 prompt 长度和输出长度下的性能
- 不同 batch size 下的吞吐
- 长时间运行下的稳定性

**常用工具**：
- vLLM 自带的 benchmark_serving.py
- TensorRT-LLM 的 benchmarks 脚本
- 自研压测工具，模拟真实请求分布

**压测要覆盖真实场景**。实验室里的理想指标，到了生产环境可能因为网络、存储、日志等因素大打折扣。

压测设计要注意以下几点：

第一，请求分布要接近真实业务。不能只用固定长度的 prompt 和固定长度的输出。真实业务中 prompt 长度可能从几十 token 到几万 token 不等，输出长度也有很大差异。

第二，要覆盖并发从低到高的全过程。从单请求开始，逐步增加并发，观察 TTFT、TPOT、吞吐的变化曲线。特别要找到 TTFT 开始明显上升的拐点。

第三，要做饱和测试。不限制并发或 QPS，压满系统，观察极限吞吐和极限延迟。极限数据用于了解系统天花板，不是上线目标。

第四，要跑稳定性测试。持续压测数小时，观察是否有显存泄漏、延迟漂移、错误率上升等问题。

## 9.6.1 压测报告模板

一份完整的压测报告应包含环境、配置、指标、瓶颈分析和上线建议。下面以 GLM-5-FP8 在 H200 8 卡集群上的压测为例，说明报告结构。

**测试环境**：
- 模型：GLM-5-FP8
- GPU：8×H200 SXM（141 GB HBM3e/卡）
- 互联：NVLink 机内 + RoCEv2 跨节点
- 并行策略：单机 TP=8
- 引擎版本：vLLM stable
- 压测工具：vLLM 官方 vllm bench serve
- 数据集：ShareGPT V3（真实对话分布）

**测试配置**：
- gpu_memory_utilization=0.9
- max_model_len=4096
- max_num_seqs=256
- max_num_batched_tokens=4096
- enable_chunked_prefill=True

**性能指标示例**：

| 测试条件 | 并发 | Req/s | Tokens/s | TTFT(ms) | TPOT(ms) |
|---------|------|-------|----------|----------|----------|
| 限速 20 RPS，最大并发 20 | 20 | 2.24 | 447 | 130 | 44 |
| 不限制，最大并发 1000 | 1000 | 9.17 | 1830 | 6769 | 731 |
| 不限制，最大并发 10000 | 10000 | 12.78 | 2560 | 335415 | 311 |

数据来源：`docs/vLLM推理引擎深度解析.md` 第十四章生产压测数据。

这组数据揭示了三个规律：

第一，吞吐量随并发增长但边际递减。从并发 20 到 1000（50 倍），吞吐从 2.24 涨到 9.17（4.1 倍）。从 1000 到 10000（10 倍），吞吐从 9.17 涨到 12.78（1.4 倍）。GPU 在 1000 并发左右已经接近饱和。

第二，TTFT 在高并发下爆炸性增长。并发 20 时 TTFT=130ms，并发 1000 时 6769ms，并发 10000 时 335415ms。增长不是线性的，因为高并发时大量请求堆积在 WAITING 队列等 Prefill。

第三，TPOT 增幅远小于 TTFT。并发 20 时 TPOT=44ms，并发 10000 时 TPOT=311ms。这验证了 Decode 是 memory-bound 的特征：每 token 时间相对恒定，不会像 Prefill 那样因为队列堆积而指数恶化。

**不同输入长度下的 TTFT 验证**：

| 场景 | 输入长度 | 并发 | P99 TTFT(ms) |
|------|---------|------|-------------|
| short_low | 128 | 1 | 72 |
| medium_low | 512 | 1 | 182 |
| long_low | 2048 | 1 | 289 |
| ultra_low | 8192 | 1 | 1028 |
| extreme_low | 32768 | 1 | 4295 |

输入从 128 涨到 32768（256 倍），TTFT 从 72ms 涨到 4295ms（60 倍）。这验证了 Prefill 是 compute-bound 的特征：prompt 越长，计算量越大，TTFT 越高。增长不是 256 倍的原因是 Prefill 计算量介于 O(N) 和 O(N²) 之间。

**TPOT 与输入长度无关的验证**：

| 场景 | 输入长度 | 并发 | P99 TPOT(ms) |
|------|---------|------|-------------|
| short_low | 128 | 1 | 26 |
| ultra_low | 8192 | 1 | 27 |
| extreme_low | 32768 | 1 | 27 |

在并发为 1 时，不管输入是 128 还是 32768 token，TPOT 都是 26–27ms。这验证了 Decode 是 memory-bound 的特征。每生成一个 token，GPU 读取一次权重矩阵。权重大小与输入长度无关，因此每 token 时间恒定。

**瓶颈分析**：
- 低并发时 TTFT 和 TPOT 都很好，瓶颈在 GPU 算力未充分利用
- 中等并发时 TTFT 开始上升，Prefill 排队成为瓶颈
- 高并发时 TPOT 也上升，batch 变大导致单次 forward pass 时间增长
- 跨节点 TP=16 时，低并发场景双机比单机慢 8%–27%，因为 all-reduce 通信开销占比大

**上线建议**：
- 生产目标吞吐应设为极限吞吐的 60%–70%。素材中 saturation_rate 场景测得单机极限约 5246 tokens/s（约 6.8 req/s），但此时 P99 TTFT 已超过 10 分钟，系统严重过载；ShareGPT 真实分布压测（上表）在 10000 并发时极限约 2560 tokens/s。无论取哪个极限，生产目标都应设在 3.5–4.5 req/s，对应并发 50–100 左右
- 这个区间 TTFT 可控（小于 1 秒），TPOT 稳定（小于 50ms）
- 超过这个区间追求吞吐，延迟会不可接受
- 如果业务对 TTFT 敏感，应限制最大并发，优先保证用户体验

## 9.7 生产中的常见问题

**显存不足**：KV Cache 增长过快。可以通过减小 max_num_seqs、增加 block size、使用量化、开启前缀缓存来缓解。

**延迟抖动**：请求长度差异大，批处理效率下降。可以设置最大等待时间、使用 chunked prefill、按 prompt 长度做路由。

**首 token 慢**：prompt 太长，Prefill 计算量大。可以增加 TP 并行数、使用更快的 attention kernel、开启前缀缓存、按 prompt 长度分流到 Prefill 专用节点。

**模型版本管理**：多版本共存、灰度发布、回滚策略需要平台支持。新模型版本上线前应先在 10% 流量上做 A/B 测试，验证 TTFT/TPOT/吞吐符合预期后再全量。

**跨节点部署性能下降**：TP=16 跨两节点时，all-reduce 要走 RoCEv2 网络。低并发时双机可能比单机慢，因为通信开销占比大。只有当并发高到把单机 GPU 完全打满时，双机的额外算力才能克服通信开销。大多数在线服务并发在几十到几百，单机 TP=8 是更优选择。

**启动失败与后端不支持**：新模型上线时，可能出现 "No valid attention backend found" 等错误。这时不能只看报错字面意思，要读 Reasons 矩阵。竖着读列，找出出现最多的不支持项。横着读行，找出最接近支持的后端。两者求交集，判断是否为版本错位。如果是版本错位，需要换镜像或换引擎版本，而不是盲目调参。

**vLLM 启动参数抄错场景**：单机部署时不要传 `--distributed-executor-backend ray`，这是双机 TP16 才需要的参数。单机走默认 mp（multiprocessing）更轻、更快、少一层依赖。抄参数不抄边界是部署翻车的常见原因。

## 9.8 这一环在整个链路中的位置

推理是 AI Infra 链路的最终输出端。

向上，它直接面向用户和业务。用户感知到的延迟、稳定性和成本，都在这里体现。

向下，它依赖训练产出的模型、平台提供的部署能力、基础设施提供的 GPU 和网络。前面的任何短板都会影响推理效果。

训练决定模型能不能诞生，推理决定模型能不能用得起、用得好。

从工程角度看，推理优化的主线很明确。第一，通过 PagedAttention 等显存管理技术提高并发。第二，通过连续批处理提高 GPU 利用率。第三，通过量化降低显存和带宽压力。第四，通过前缀缓存和 PD 分离降低长上下文成本。最后，通过压测找到延迟和吞吐的平衡点。每一项技术都不是孤立的，它们共同决定了一个推理服务的成本和体验。

实际部署时，不要追求单点最优，而要追求系统最优。一个参数在实验室里可能表现最好。但到了生产环境，它可能因为请求分布、网络状况、资源竞争而失效。因此，压测和监控是推理服务上线的必要步骤。没有数据支撑的优化都是猜测。好的推理工程师不是参数调得最好的人，而是能用数据讲清楚"为什么这样配"的人。

## 小结

推理是长期运营，优化目标是单位成本下服务更多用户。Prefill 是算力密集型，Decode 是访存密集型，KV Cache 是显存主要消耗。vLLM、TensorRT-LLM 和 SGLang 各有适用场景，量化、前缀缓存、PD 分离和连续批处理是核心优化手段。上线前必须按真实请求分布做压测，在延迟和吞吐之间找到业务可接受的平衡点。
